# Phase 03.6 Plan 02: Per-Region Fan-Out Launcher + Single-Region Job Body Summary

**A capstone launcher (`submit_allocation_scenario.sh`) that resolves the region list and timestep schedule from `get_config()`, fans out one highmem `submit_allocation_region.sh` job per region (resuming each from its last completed timestep), and chains an `afterok` national-mosaic-assembly job on all region ids — the reproducible D-04 recipe, scenario-parameterised for Phase 4.**

## Accomplishments

- **D-01/D-02 single-region job body (`scripts/submit_allocation_region.sh`):** a highmem SBATCH job (`--partition=highmem --exclusive --mem=0 --cpus-per-task=40 --time=24:00:00`) that runs ONE region's full serial timestep chain under `ALLOCATION_REGION_FILTER`. It reads the region from `ALLOC_REGION` (set by the launcher), fails closed (exit 2) if `ALLOC_REGION` is unset (a region-less submit would silently run all regions and OOM), reuses the `hpc_common.sh` env-activation boilerplate verbatim (`setup_common_env` / `activate_env "$ENV_PATH"` with `ENV_NAME=allocation_env` / `RSCRIPT_BIN=$(verify_rscript "$ENV_PATH")`), leaves `ALLOCATION_YEAR_POST_FILTER` as whatever the launcher exported (resume-aware), passes through `ALLOCATION_PREDICT_BATCH_ROWS`/`PREDICTOR_LAZY`/`PREDICT_NUM_THREADS` (andes needs batched predict for the 26M-cell from-class), and launches `scripts/run_allocation.r` via the verified `RSCRIPT_BIN`. Safe to run concurrently with sibling regions because Plan 01 D-05 makes a single-region run chain on its own `region_<suffix>/posterior.tif` and skip the shared national mosaic.
- **D-04/D-09 launcher (`scripts/submit_allocation_scenario.sh`):** NOT itself an SBATCH job — it calls `sbatch`. It resolves the region label list, `simulation_year_steps`, and `simulation_output_dir` from inline `get_config()` / `regions.json` probes (nothing hardcoded), then for each region: (a) derives `region_suffix` via `tr ' ' '_' | tr '[:upper:]' '[:lower:]'` (matches `allocation.r:862` `gsub(" ","_",tolower())`); (b) implements timestep resume (D-09) by scanning `<sim_out>/<SCENARIO>/<year>/region_<suffix>/posterior.tif` over the posterior years and finding the first incomplete one, exporting `ALLOCATION_YEAR_POST_FILTER` only when earlier posteriors already exist (skipping a fully-complete region entirely); (c) submits the per-region job with `sbatch --parsable --partition=<per-region> --export=ALL,ALLOC_REGION=<label>,ALLOC_SCENARIO=<scenario>[,ALLOCATION_YEAR_POST_FILTER=<resume>]`, capturing the id into a colon-joined list. After all regions it queues `sbatch --dependency=afterok:<id-list> --parsable --export=ALL,ALLOC_SCENARIO=<scenario> scripts/submit_assemble_mosaic.sh` (the Plan 03 target, referenced by name). It fails closed (exit 1) when the region probe returns zero regions (T-036-04) and emits a structured `STATE launcher=...` summary line.
- **Scenario parameterisation (Phase 4 S2 reuse):** both scripts take `ALLOC_SCENARIO` (BAU default) so the same recipe generalises to the multi-scenario sweep without code changes.

## Decisions Made

- **Explicit bash loop, not a SLURM array** (Claude's Discretion per CONTEXT D-disc) — per-region `--partition`/`--mem` need to differ by region (forest-dominated regions peak higher), which a `--array` cannot express cleanly. A loop over `${REGIONS[@]}` with per-iteration `sbatch` is the right shape and matches the `master_pipeline.sh` submission idiom.
- **Per-region partition map** — `cuenca_del_amazonas` / `selva_andina` default to a `fat` node (they preload ~80GB and spike >128GB on the big forest->* transition per `submit_allocation_smoke.sh` header notes); all other regions default to `highmem`. Overridable via `ALLOC_PARTITION` / `ALLOC_FAT_PARTITION`.
- **Resume on the FIRST incomplete posterior year** — `ALLOCATION_YEAR_POST_FILTER` is exported only when earlier posteriors already exist; if the first posterior year is incomplete the full chain runs from the schedule start (no filter), and a fully-complete region is skipped (no job submitted). Posterior years are `tail(simulation_year_steps, -1)` (year-ends), since each timestep writes `posterior_<year_end>`.
- **Mosaic job referenced by name (`submit_assemble_mosaic.sh`)** even though Plan 03 creates it — the launcher and assembler are co-delivered this phase, so the `afterok` target is wired now and the assembler lands in Plan 03 (matches the plan's `<action>` and `<verification>`).
