# Phase 3.5 Validation — Andes (`selva_andina`/`andes`)

Validation of the two Phase 3.5 changes against the canonical hard forest case:
- **Goal 1** — lazy per-from-class predictor reads (`ALLOCATION_PREDICTOR_LAZY`, default on)
- **Goal 2** — scoped multi-threaded ranger prediction (`ALLOCATION_PREDICT_NUM_THREADS`, auto)

All numbers are real HPC smoke runs (region `andes`, scenario BAU, year_post 2026).
The controlled comparison is **lazy+160thr (573721) vs eager+160thr (573776)** — same
region, same thread count, differing only in the predictor read path — plus the
quantified job-**571309** baseline (selva_andina, BAU, 1-thread eager, 2026-06-22) as a
cross-region reference.

> **Region note:** `andes` is a *larger* region than the `571309` baseline's
> `selva_andina` (per-from-class cell counts sum to ~41.8M; the eager preload reported
> 42,869,798 region cells, vs 30,822,155 for selva_andina). The 571309 baseline is
> therefore a cross-region reference, not a like-for-like control; the like-for-like
> control is the andes-eager run (573776).

## Two-stage isolation (Goal 2 — threading)

Dominant predict (from-class 102 = natural_grasslands, 26,043,137 cells), transition 102→105:

| Threads | predict elapsed | speedup vs 1thr |
|---|---|---|
| 1 (573683) | 4738.850 s | 1× |
| 40 (573683, highmem) | 275.307 s | 17.2× |
| 160 (573721, fat) | 133.584 s | **35.5×** |

Threading scales sublinearly (memory-bandwidth bound — 160 threads ≈ 35× not 160×), but
the win is decisive. `setup_inputs` dropped from the 20665 s baseline to **2283 s** with
lazy+160thr — comfortably beating the Phase 4 SC#2 ≥3× target (≈9×).

## Numerical equivalence (Pitfall 3/4)

`compare_prob_maps.r` over all 24 probability TIFs, **lazy+160 (573721) vs eager+160 (573776)**:

```
OVERALL max|delta| over 24 common tifs = 0.000e+00  (worst: NA)
VERDICT: BIT-FOR-BIT IDENTICAL
```

- **max|Δ| = 0.000e+00** on every transition, **NA-mismatch = 0** on every transition.
- This is *stronger* than the plan's requirement (bit-for-bit at 1thr; <1e-6 at threads):
  the lazy read path produces **exactly** the eager result even at 160 threads — ranger's
  threaded prediction is deterministic here, so there is no FP-reorder noise to tolerate.
- **Per-transition cell counts are identical** by construction (identical TIFs, identical
  coverage): 102=26,043,137 · 103=8,148,796 · 105=5,465,689 · 101=1,729,302 · 104=409,191.
  No Pitfall-4 coverage loss.

## A3 verdict — does the lazy per-from-class scan beat the eager preload in aggregate?

**Settled: lazy is NOT the aggregate loss A3 feared — it is competitive / marginally better end-to-end.**

- Isolated read: lazy Σ scans **~111 s** vs eager preload **87.8 s** → lazy ~26% slower *on the read alone* (not the catastrophic re-scan blow-up A3 worried about).
- End-to-end: lazy `setup_inputs` **2283 s** < eager **2389 s** → lazy is ~4% *faster* overall (the eager full-region resident table adds GC pressure that offsets its faster read).
- **Bisect fallback recorded:** `ALLOCATION_PREDICTOR_LAZY=0` reverts to the eager path
  byte-for-byte (proven — that is exactly run 573776). Command:
  `ALLOCATION_PREDICTOR_LAZY=0 sbatch scripts/submit_allocation_smoke.sh`.

## Residual-floor assessment (honest)

**Goal 1's memory-floor reduction is real but modest *on andes*, and the run's peak is NOT lower than baseline — because the peak is driven by the predict transient, not the predictor read:**

- Lazy cut the **resident** floor ~20 GB on andes (eager ~91 GB vs lazy ~70 GB) and removed the one-shot eager preload. But the **peak RSS (~206–216 GB)** is dominated by the single-shot ranger predict transient on the 26M-cell from-class 102 — nearly identical for lazy and eager. The ~10–20 GB target is **not** met for peak in single-shot mode.
- **Why andes is undersold:** andes' eager preload is only +23.9 GB. The motivating ~80 GB preload floor is the **Amazon** (`cuenca_del_amazonas`), where lazy's per-from-class bound delivers the large win. The andes result confirms lazy is *correct, equivalent, and competitive*; the headline memory benefit will land on the Amazon.
- **Dominant remaining RSS terms:** (1) the predict transient on class 102 (~100–130 GB on top of resident), (2) 45 GB of resident preloaded models, (3) the long-format `gather` accumulation across transitions. The lazy per-from-class cache (`new.env`, no eviction) accumulates toward region size by end-of-loop — a candidate follow-up (evict prior from-class after its transitions) but not the peak driver.
- **Recommendation for big forest regions (Amazon):** combine lazy + threading with
  **`ALLOCATION_PREDICT_BATCH_ROWS`** (Phase 3.4) to cap the predict transient. With lazy
  resident ~70 GB + a batched transient, peak drops well under a 188 GB highmem node.
  Single-shot on andes peaks ~206 GB → needs a fat node or batching.

## Caveat — mlr3 predict path broken (environment drift, pre-existing, not Phase 3.5)

Every transition logs:
`mlr3 predict_newdata() failed (could not find function ".__Task__col_info"); falling back to direct model prediction`.

The mlr3 learner predict path is non-functional in the current `allocation_env` (mlr3
version vs saved-model drift), so all predictions use the **direct ranger fallback**. The
fallback honors `num.threads` (threading works) and is deterministic (bit-for-bit across
runs), so it does not affect this validation's conclusions — but it likely inflates the
predict transient vs the intended mlr3 path and warrants a separate fix.

## Bug found & fixed during validation

The lazy read initially failed at the first prediction on every run (`In index: 1`, masked
by `furrr`): the Arrow join-key table was `int32` (from `as.integer()`) while the parquet
`cell_id` is `int64`, so Acero's hash-join could not match. Fixed in
`fix(03.5-02): cast lazy predictor join key to dataset cell_id type` (commit d314504) by
casting the key table to each dataset's own `cell_id` type. The local testthat suite could
not catch this (arrow `SKIP`s without an install); the HPC smoke is the validation
mechanism (per REQUIREMENTS.md).
