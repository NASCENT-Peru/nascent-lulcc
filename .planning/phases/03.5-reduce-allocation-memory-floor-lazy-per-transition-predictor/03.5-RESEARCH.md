# Phase 3.5: Reduce Allocation Memory Floor — Research

**Researched:** 2026-06-23
**Domain:** R allocation prediction path — lazy Arrow predictor reads + threaded ranger prediction in `src/allocation.r`
**Confidence:** HIGH (code claims verified by direct file reads; library-behaviour claims verified against official docs + the codebase's own corroborating comment)

---

## Summary

Phase 3.5 makes two surgical changes to the prediction path in `src/allocation.r`'s `generate_probability_maps()` to flip the regional allocation sweep from memory-bound to core-bound:

1. **Lazy per-transition (really per-from-class) predictor reads.** Today, `preload_region_predictor_data()` (L1935) does one big `arrow::open_dataset() |> filter(region) |> select(all_cols) |> collect()` into `region_pred_dt` (L2183) — the FULL region predictor table (all ~38 columns × every cell). For the Amazon's 68M cells this is the ~80 GB floor. The fix: replace the eager up-front collect with on-demand Arrow scans scoped to (a) only the columns one model needs and (b) only the cells in that transition's "from" class. Because N transitions share a small set of distinct from-classes (often 4–8), the right granularity is **per-from-class, cached**, not per-transition — this is the single most important design decision in the phase. The existing code at L2157–2169 already opens the hive-partitioned static + dynamic datasets lazily; the gap is purely that the preload collects everything.

2. **Threaded ranger prediction.** `predict_saved_transition_prob()` pins ranger to `num.threads = 1L` (direct-fallback L1059) and the mlr3 learner inherits mlr3learners' default of 1 thread. The run is memory-bound with idle cores, so the large from-class predictions (tens of millions of rows) can use `num.threads > 1` to cut wall time. The constraint is `threads × workers ≤ cores`, and the relaxation must be **scoped to the ranger predict call only** — `pin_native_threads_to_one()` (L194) must stay in force for BLAS/data.table/arrow to avoid oversubscription and the Lustre IO-thread deadlock noted at L210–214.

The Andes (`selva_andina`) is the validation region per the operator directive. The 571309 baseline shows the Andes preload is cheap (167s / +13.7 GB / 59.4 GB peak) — the dominant cost is the per-transition prediction loop inside `setup_inputs` (~5.7 h, loop peak ~94 GB). So **Goal 2 (threading) is the lever that the Andes smoke proves for wall time; Goal 1 (lazy reads) is the lever that matters for the Amazon's 80 GB floor.** The plan must ship both but validate throughput primarily on the Andes.

**Primary recommendation:** Add a per-from-class lazy predictor reader (`load_from_class_predictor_data()`) that does `inner_join` against an Arrow table of the from-class `ref_cell_id` keys with column projection to just the union of predictors needed by transitions sharing that from-class, cached across transitions. Gate it behind a default-ON env knob `ALLOCATION_PREDICTOR_LAZY` (with `=0` escape hatch to the current eager preload for bisecting). Add a `num.threads` knob `ALLOCATION_PREDICT_NUM_THREADS` (auto-derived default `floor(cores / workers)`, clamped ≥1), applied to BOTH the mlr3 learner `param_set` and the direct ranger fallback, scoped to predict only. Compose with `ALLOCATION_PREDICT_BATCH_ROWS` (Phase 3.4) by batching AFTER the lazy read.

### Pattern 1: Per-from-class lazy predictor read (the core change)

**What:** Read predictors lazily, scoped to one from-class's cell keys + the union of columns its transitions need, cached so transitions sharing a from-class reuse one collect.

**When to use:** Replaces `preload_region_predictor_data()` call (L2183) and the per-transition `region_pred_dt[J(lookup_keys)]` lookup (L2286–2308) when `ALLOCATION_PREDICTOR_LAZY` is on (default).

**Example:**
```r
# Source: NEW function for src/allocation.r — design pattern, verify against
# ds_static/ds_dynamic schemas at L2157-2169.
load_from_class_predictor_data <- function(ds_static, ds_dynamic,
                                           cols, region_value, scenario,
                                           ref_cell_keys, log_file = NULL) {
  cols <- unique(as.character(cols))
  static_cols <- intersect(cols, names(ds_static$schema))
  dyn_cols    <- intersect(cols, names(ds_dynamic$schema))

  # Arrow table of the sparse from-class keys — join is the FAST path; a bare
  # filter(cell_id %in% ref_cell_keys) on a multi-million-element vector is the
  # slow path the L2176-2179 comment warns about (see Pitfall 1).
  key_tbl <- arrow::arrow_table(cell_id = as.integer(ref_cell_keys))

  static_df <- if (length(static_cols)) {
    ds_static |>
      dplyr::filter(region == !!region_value) |>
      dplyr::select(cell_id, dplyr::all_of(static_cols)) |>
      dplyr::inner_join(key_tbl, by = "cell_id") |>
      dplyr::collect() |>
      data.table::as.data.table()
  } else data.table::data.table(cell_id = integer())

  dyn_df <- if (length(dyn_cols)) {
    ds_dynamic |>
      dplyr::filter(region == !!region_value, scenario == !!scenario) |>
      dplyr::select(cell_id, dplyr::all_of(dyn_cols)) |>
      dplyr::inner_join(key_tbl, by = "cell_id") |>
      dplyr::collect() |>
      data.table::as.data.table()
  } else data.table::data.table(cell_id = integer())

  result <- if (nrow(static_df) && nrow(dyn_df)) {
    merge(static_df, dyn_df, by = "cell_id", all = TRUE)
  } else if (nrow(static_df)) static_df else dyn_df
  data.table::setkeyv(result, "cell_id")
  result
}
```

### Pattern 2: Per-from-class cache keyed by from_val

**What:** Many transitions share a from-class (e.g. all `forest -> *` transitions). Read each distinct from-class once.

**When to use:** In the per-transition loop at L2206; check the cache before scanning.

**Example:**

from_class_cache <- new.env(parent = emptyenv())  # keyed by as.character(from_val)

### Pattern 3: Scoped `num.threads` relaxation for predict only

**What:** Set `num.threads` on the ranger learner / fallback for the predict call while leaving `pin_native_threads_to_one()` in force for everything else.

**When to use:** In `predict_saved_transition_prob()` mlr3 path (L1038) and fallback (L1059).

**Example:**
```r
# Source: NEW resolver, mirrors get_allocation_predict_batch_rows() at L519
get_allocation_predict_num_threads <- function() {
  raw <- Sys.getenv("ALLOCATION_PREDICT_NUM_THREADS", unset = "")
  workers <- suppressWarnings(as.integer(Sys.getenv("ALLOCATION_NUM_WORKERS", "1")))
  if (is.na(workers) || workers < 1L) workers <- 1L
  cores <- suppressWarnings(as.integer(Sys.getenv("SLURM_CPUS_PER_TASK", "")))
  if (is.na(cores) || cores < 1L) {
    cores <- tryCatch(parallel::detectCores(logical = TRUE), error = function(e) 1L)
  }
  if (nzchar(raw)) {
    t <- suppressWarnings(as.integer(raw))
    if (is.na(t) || t < 1L) t <- 1L
  } else {
    t <- max(1L, cores %/% workers)        # auto: threads × workers ≤ cores
  }
  # Hard clamp so a misconfigured knob can never oversubscribe:
  max(1L, min(t, cores %/% max(1L, workers)))
}

# mlr3 path (replaces / wraps L1040):
nthreads <- get_allocation_predict_num_threads()
try(model_obj$learner$param_set$set_values(num.threads = nthreads), silent = TRUE)
pred_attempt <- tryCatch(model_obj$learner$predict_newdata(newdata = block),
                         error = function(e) e)

# direct ranger fallback (replaces hardcoded 1L at L1059):
raw <- predict(underlying, data = block, num.threads = nthreads)
```

### Anti-Patterns to Avoid

- **Un-pinning OMP globally to get ranger threads.** Setting `OMP_NUM_THREADS > 1` (or calling `RhpcBLASctl::omp_set_num_threads(N)`) un-pins BLAS/GDAL too, causing oversubscription against data.table/arrow and risking the Lustre IO deadlock (L210–214). Pass `num.threads` to the ranger call directly; ranger's OpenMP region honours its own `num.threads` argument over the env default. [CITED: rdocumentation.org predict.ranger num.threads]
- **`filter(cell_id %in% big_vector)`.** The known-slow path (the codebase's own L2176–2179 comment). Use an `inner_join` against an Arrow key table instead (Pattern 1, Pitfall 1).
- **Re-scanning the dataset per transition.** Cache per from-class (Pattern 2). N transitions, ~4–8 from-classes.
- **Batching before the lazy read.** Batch the materialised from-class frame, not the Arrow query. Keep the Phase 3.4 batch loop (L1097–1122) downstream of the read.
- **Dropping the eager path entirely.** Keep it behind `ALLOCATION_PREDICTOR_LAZY=0` so a regression can be bisected against the known-good 571309 path.
- **Removing the keyed in-memory join (L2288–2308).** It still works — just against a from-class-sized table instead of a region-sized one. Reuse it.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Sparse key selection from Parquet | Custom row-group reader / manual offset math | Arrow `inner_join(arrow_table(keys))` + column `select()` | Acero pushes the join + projection into the scan; row-group stats prune on cell_id (data is cell_id-sorted within region — see Q1). |
| Keyed predictor lookup on the materialised frame | New join routine | Existing `data.table` keyed join at L2288–2308 | Already correct; just feed it the from-class subset. |
| Thread-count arithmetic | Inline `cores/workers` scattered in two call sites | One `get_allocation_predict_num_threads()` resolver | Single source of truth; mirrors `get_allocation_predict_batch_rows()` (L519). |
| Row-batched prediction | Re-implement batching | Existing `ALLOCATION_PREDICT_BATCH_ROWS` loop (L1097–1122) | Phase 3.4 already did this; compose. |
| Predictor column union per from-class | Manual per-transition column tracking | `split(model_info$predictor_names, from_val)` + `unique(unlist())` | Base R; one pre-loop pass. |

**Key insight:** The whole phase is composition + scoping, not new machinery. Lazy datasets are already open (L2157). The keyed join already exists (L2288). The batch loop already exists (L1097). Ranger/mlr3 already expose `num.threads`. The work is: (1) swap the eager collect for a cached per-from-class lazy read, and (2) thread one resolver through two predict call sites.

## Common Pitfalls

### Pitfall 1: `filter(cell_id %in% big_vector)` is the slow Arrow path (the whole reason the eager preload exists)

**What goes wrong:** Expressing the sparse-key filter as `dplyr::filter(cell_id %in% from_class_keys)` against the dataset is slow for multi-million-element key vectors. The codebase already discovered this — the comment at `src/allocation.r:2176–2179` says per-transition `cell_id %in%` Arrow filters were "very slow," which is precisely why the eager region preload was introduced. If the lazy redesign reintroduces `%in%` it will be slower in aggregate than the eager scan it replaces and the phase fails its own goal.

**Why it happens:** Acero evaluates a large in-list as a per-row membership test across every scanned fragment; it does not get the partition-pruning shortcut a partition-key filter gets, and a giant literal list is expensive to materialise into the plan.

**How to avoid:**
1. Use `inner_join(arrow_table(keys), by = "cell_id")` (Pattern 1) — Acero treats this as a hash-join that pushes down to the scan, far cheaper than a giant `%in%`.
2. Cache per from-class so the scan happens ~(#distinct from-classes) times, not N times (Pattern 2).
3. Leverage row-group pruning: cell_id is monotonic within each region partition (verified in `create_predictor_parquets.r`), so a contiguous-ish from-class key set skips row groups whose [min,max] cell_id misses — but only the join/filter expressed on cell_id benefits; keep keys as integers matching the schema type.

**Warning signs:** Per-transition `stage=predictor_load` elapsed in the smoke log climbs higher than the old single `stage=predictor_preload` (167s baseline) summed; total `setup_inputs` gets WORSE not better. Falsifiable: see Validation.

### Pitfall 2: Relaxing `num.threads` by un-pinning OMP causes oversubscription / Lustre deadlock

**What goes wrong:** The naive way to "let ranger use more threads" is to raise `OMP_NUM_THREADS`. But that also un-pins BLAS, GDAL, and (if arrow IO threads follow) risks the exact Lustre/beegfs executor deadlock the L210–214 comment documents. With multiple workers, un-pinned BLAS × workers × ranger threads oversubscribes the node.

**Why it happens:** ranger's training/prediction OpenMP region defaults to the env thread count when `num.threads` is unset, so people reach for the env var. But ranger honours an explicit `num.threads` argument passed to `predict()` over the env default.

**How to avoid:** Leave `pin_native_threads_to_one()` (L194) fully in force. Pass `num.threads = T` directly to the ranger predict call (Pattern 3). Do NOT touch `OMP_NUM_THREADS`, `RhpcBLASctl::omp_set_num_threads`, `arrow::set_cpu_count`, or `data.table::setDTthreads`. The relaxation is one argument on one function call, nothing global.

**Warning signs:** Load average > cores during predict; BLAS-heavy steps slow down; arrow collect hangs on the shared filesystem (the L210–214 failure mode).

### Pitfall 3: Threading non-determinism breaks numerical equivalence

**What goes wrong:** Random forest *prediction* is a deterministic average over trees regardless of thread count (no RNG in predict), so `num.threads > 1` should produce bit-identical probabilities to `num.threads = 1`. BUT floating-point summation order can differ across thread partitions, producing tiny (~1e-15) differences that, after the per-cell normalization (L2400–2402) and `terra::writeRaster` to FLT4S, are far below the raster's float precision. The risk is only if someone assumes EXACT byte equality of TIFs.

**Why it happens:** Parallel reduction sums trees in a different order per run.

**How to avoid:** Validate equivalence with a tolerance (e.g. `max(abs(prob_lazy_threaded - prob_eager_1thread)) < 1e-6`), not bit-for-bit on the TIFs. The lazy-read change itself (Goal 1) MUST be bit-for-bit (same cells, same columns, same model → same input → same output); only the threading change (Goal 2) needs the tolerance. Test the two changes independently so a mismatch localises.

**Warning signs:** Probability rasters differ by more than ~1e-6; or differ between two runs at the SAME thread count (that would indicate a real bug, not FP reordering).

### Pitfall 4: Lazy read drops cells the eager path kept (silent throughput loss)

**What goes wrong:** `inner_join` against from-class keys returns only cells present in BOTH the dataset and the key set. The eager path used `region_pred_dt[J(lookup_keys), nomatch = NA]` (L2292) — it KEEPS keys missing from the predictor table, filling NA. If the lazy `inner_join` silently drops cells the predictor parquet is missing, those cells get no prediction and the transition's probability map loses coverage vs. the baseline.

**Why it happens:** `inner_join` vs `nomatch=NA` left-join semantics differ.

**How to avoid:** After the cached read, keep the SAME `region_pred_dt[J(lookup_keys), nomatch = NA]` keyed-join semantics at L2288–2308 (the from_data still left-joins against the from-class table). The lazy read just changes WHICH rows are in `region_pred_dt`; the downstream join behaviour (NA-fill for missing predictor rows) is unchanged. Validate: per-transition cell count (logged at L2477–2488 "%d cells") must equal the baseline per-transition cell count for `selva_andina`.

**Warning signs:** `stage=raster_write` log "%d cells" lower than baseline for any transition; saturation drops in the downstream Dinamica run.

### Pitfall 5: `num.threads` not actually applied to the mlr3 learner

**What goes wrong:** Setting `param_set$set_values(num.threads = N)` on a learner whose stored ranger model already fixed threads, or on the wrong object, silently no-ops — prediction stays single-threaded and the wall-time win never materialises.

**Why it happens:** mlr3learners sets the `classif.ranger` `num.threads` default to 1 (changed from ranger's own default to avoid conflicting with `future`). The param is tagged `threads`; `set_threads()` is the idiomatic setter but `param_set$set_values(num.threads = N)` also works. The fallback path (direct `predict.ranger`) needs its OWN `num.threads` argument — setting the learner param does not affect the fallback.

**How to avoid:** Apply the thread count in BOTH places (Pattern 3): the learner `param_set` for the mlr3 path AND the explicit `num.threads=` arg in the fallback `predict(underlying, ...)`. Add a log line echoing the resolved thread count so the smoke log proves it took effect. [CITED: mlr3learners.mlr-org.com classif.ranger — num.threads default 1, tag threads]

**Warning signs:** `stage=predict` wall time unchanged after the threading change; CPU stays at ~1 core during predict.

### Pitfall 6: Composition with `ALLOCATION_PREDICT_BATCH_ROWS` double-counts memory

**What goes wrong:** The batch loop (L1097–1122) bounds the predict-time copies. If the lazy read materialises the whole from-class frame AND the batch loop also holds a slice, peak = from-class frame + one batch + ranger's internal copy. For the Amazon's largest from-class (forest, tens of millions of cells) the from-class frame itself may still be several GB even though it is far below the 80 GB region floor.

**Why it happens:** The lazy read bounds memory by from-class size, not batch size; batching bounds the predict copies, not the input frame.

**How to avoid:** This is acceptable and expected — the from-class frame is the irreducible input. The combination (lazy read bounds the FRAME to from-class size; batching bounds the predict COPIES to batch size) is exactly the intended stack. Document the residual: peak ≈ largest-from-class-frame + batch_copy + model. Set `ALLOCATION_PREDICT_BATCH_ROWS` for the Amazon as today; the Andes likely does not need it.

**Warning signs:** Amazon peak RSS still > ~20 GB after lazy reads — likely the forest from-class frame; tune `ALLOCATION_PREDICT_BATCH_ROWS` and report honestly (the ~10–20 GB target may need a follow-up if a single from-class frame exceeds it).

## Open Questions

### Q1 — Lazy per-transition Arrow read design (the central question)

**What we know:**
- Datasets are already opened lazily (L2157–2169), hive-partitioned by `region` (static) and `scenario,region` (dynamic).
- The eager preload exists *specifically because* per-transition `cell_id %in%` filters were "very slow" (L2176–2179 comment — a first-party finding).
- **cell_id is monotonic within each region partition** (verified: `create_predictor_parquets.r` streams `row_idx`-ordered chunks, L499–559), so row-group [min,max] statistics on cell_id enable pruning for a key-based read.
- N transitions share few distinct from-classes (the modelling output is `{from_class}-{to_class}` files; a region with ~6 LULC classes has ≤6 from-classes feeding ≤~30 active transitions).

**Resolution (HIGH confidence on the WHY; MEDIUM on the exact best primitive):**
- **WHY `%in%` was slow:** Acero evaluates a large in-list as a per-row membership predicate across every scanned fragment and gets no partition-pruning shortcut (the partition key is `region`, not `cell_id`). A multi-million-element literal in-list is also costly to embed in the plan.
- **HOW to avoid it now:** (a) express the key selection as `inner_join(arrow_table(keys), by="cell_id")` — a hash-join that Acero pushes into the scan and that, combined with cell_id-monotonic row groups, prunes; (b) read **once per distinct from-class** (cache, Pattern 2) so the dataset is scanned ~(#from-classes) times, not N times; (c) project only the column-union that from-class needs.
- **Tradeoff quantified:** Eager = 1 scan of all 38 cols × all cells (167s/13.7GB-delta for the Andes). Lazy per-from-class = ~(#from-classes ≈ 4–8) scans, each of ~(cols for that class) × (that from-class's cells, a subset). Net read work is LESS total column×row bytes (column projection + cell subsetting) but MORE scan setups. The from-class caching is what keeps the scan-count small enough that the lazy path wins. **This must be measured (Q5) — it is the phase's central risk.**

### Q2 — Memory floor target

**What we know / residual RSS breakdown (after lazy reads):**
1. **`anterior_dt`** — the sparse cell index (cell_id,x,y,lulc_class,ref_cell_id) for all valid cells. For the Amazon's 68M cells this is ~5 ints/doubles × 68M ≈ a few GB. This is "the only full-extent table held" (L2113 comment) and is **unavoidable** — it is the floor's hard component.
2. **Resident model objects** — ALL active-transition models loaded at once (L629, A5). MEM-04 caps each < 200 MB; ~26 active ⇒ ~few GB.
3. **Largest single from-class predictor frame** — the new dominant transient. Forest from-class on the Amazon: tens of M rows × ~30 cols ⇒ potentially 5–15 GB. Bounded by from-class size, not region size — this is the whole win, but it is also the term most likely to exceed 20 GB (A4).
4. **`gather` accumulation list** — long-format (row_idx,from,to,cell_id,x,y,prob) appended per transition, held until normalization (L2378–2395). Sized by Σ(from-class cells over all transitions) — could be large for the Amazon. NOT reduced by lazy reads; a known residual.
5. **ranger internal copies during predict** — bounded by `ALLOCATION_PREDICT_BATCH_ROWS`.

**Resolution (MEDIUM confidence):** The ~10–20 GB target is plausible for the Amazon IF the largest from-class frame + `gather` + `anterior_dt` together stay under it. The biggest unknowns are the forest from-class frame size and `gather`. **Honest assessment: the target may be met for most from-classes but the single largest (forest) plus the cumulative `gather` could push it to 20–30 GB; this is still a 3–4× reduction from 80 GB and flips the Amazon onto a 188 GB highmem node comfortably with room for 4+ regions.** Recommend the plan measure the per-from-class frame sizes on the Amazon and, if needed, (a) tighten column projection per transition rather than per from-class, or (b) flush `gather[[j]]` to a scratch parquet and re-read at normalization. Surface this in validation rather than asserting the target is hit.

### Q3 — Threaded ranger prediction

**What we know (HIGH confidence):**
- `predict.ranger` `num.threads`: "Number of threads. Default is number of CPUs available." Prediction parallelises over trees via OpenMP. [CITED: rdocumentation.org predict.ranger]
- mlr3learners `classif.ranger` `num.threads`: default 1 (changed from ranger's default to avoid conflicting with `future`), tag `threads`, set via `param_set$set_values(num.threads=N)` or `set_threads()`. [CITED: mlr3learners.mlr-org.com classif.ranger]
- ranger honours an explicit `num.threads` argument over the `OMP_NUM_THREADS` env default (Issue #339 context: people see oversubscription when they DON'T pass num.threads and rely on env; passing it explicitly is the fix).

**Interaction with the pins:** `pin_native_threads_to_one()` sets `OMP_NUM_THREADS=1` etc. Passing `num.threads = T` to the ranger predict call overrides the OMP default for *that OpenMP region only* — BLAS/GDAL/data.table/arrow stay at 1. This is the desired scoped relaxation. Do NOT call `RhpcBLASctl::omp_set_num_threads` or change the env (Pitfall 2).

**Safe `num.threads` formula:** `floor(cores / workers)`, clamped ≥1, where `cores = SLURM_CPUS_PER_TASK` (or `parallel::detectCores()` fallback) and `workers = ALLOCATION_NUM_WORKERS`. The smoke runs `ALLOCATION_PARALLEL_STRATEGY=sequential` with `ALLOCATION_NUM_WORKERS = SLURM_CPUS_PER_TASK` (smoke script L78) — note: in sequential mode there is effectively ONE worker doing the region serially, so the formula should treat sequential strategy as `workers=1` and give predict ALL cores. **Recommend:** when `ALLOCATION_PARALLEL_STRATEGY=sequential`, `workers_effective = 1` ⇒ `num.threads = cores`. The plan must read the strategy to set the denominator correctly (the current smoke sets `ALLOCATION_NUM_WORKERS=4` even in sequential mode, which would wrongly cap threads at cores/4).

### Q4 — Env-knob / config surface

**Resolution (HIGH confidence on naming convention):**
- **`ALLOCATION_PREDICTOR_LAZY`** — default ON (`1`/unset = lazy). `=0` reverts to the eager `preload_region_predictor_data()` path for bisecting. Default-on is the right call because PERF-02 is a hard requirement and the Amazon cannot run otherwise on a non-fat node; the escape hatch protects against a lazy-path regression.
- **`ALLOCATION_PREDICT_NUM_THREADS`** — auto-derived default (`floor(cores/workers_effective)`); explicit integer overrides. Mirrors `ALLOCATION_PREDICT_BATCH_ROWS`'s resolver shape (L519).
- Both echoed in `scripts/submit_allocation_smoke.sh` like the L96 batch-rows echo.
- **Default behaviour reproducibility:** lazy read is bit-for-bit equivalent to eager (same cells, columns, model); threading default `> 1` introduces only FP-reordering noise (Pitfall 3). For strict reproducibility runs, operators can set `ALLOCATION_PREDICT_NUM_THREADS=1`.

### Q6 — Risks / landmines

- **Numerical equivalence:** lazy read MUST be bit-for-bit (Goal 1); threading within 1e-6 (Goal 2). Test separately. (Pitfall 3, 4.)
- **Threading non-determinism:** acceptable FP reordering; no RNG in predict. (Pitfall 3.)
- **Arrow scan overhead on beegfs/Lustre:** the L210–214 comment warns IO-thread pinning deadlocks on Lustre. Lazy reads do MORE, smaller scans — monitor for collect hangs. Keep `arrow::set_cpu_count(1)` (do NOT relax arrow threads). The `inner_join` runs in Acero, not extra IO threads. (Pitfall 1, 2.)
- **Composition with `ALLOCATION_PREDICT_BATCH_ROWS`:** lazy read first, batch the materialised frame second. (Pitfall 6.)
- **Not breaking costa_peruana / cuenca_del_amazonas:** the lazy path is region-agnostic; the escape hatch (`=0`) preserves the exact old behaviour. Smoke costa_peruana (small, fast) as a regression check after the Andes.
