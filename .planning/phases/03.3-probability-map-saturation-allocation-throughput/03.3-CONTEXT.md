# Phase 3.3: Probability Map Saturation & Allocation Throughput - Context

**Gathered:** 2026-05-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Eliminate the row-position misalignment between `trans_rates.csv`, the probability-map cube
(`probability_map_dir/*.tif`), `expansion_table.csv`, and `patcher_table.csv` so Dinamica's
Expander + Patcher operate on the correct probability map for each transition. Phase 3.1
observed ~1% allocation throughput (4,477 of hundreds of thousands of requested cells, 100%
in a single 103→105 lane) for BAU × costa_peruana × 2022→2026. The user has empirically
confirmed — by manually correcting the probability map row order on the Phase 3.1 run —
that fixing the alignment unlocks the bulk of the demanded transitions. This phase makes the
alignment correct by construction, adds a diagnostic to detect any future regression or
genuine probability-map saturation, and verifies the throughput floor on the first
simulation timestep across all Peruvian regions for BAU.

Phase 3.3 does NOT cover Patcher parameter tuning, Expander rebalancing, probability map
post-processing (floor / smoothing / rescaling), or reviving the commented-out
`calibrate_allocation_parameters` monte-carlo pipeline. Those are remediation knobs reserved
for a follow-up if the alignment fix alone does not clear the per-transition floor.

</domain>

<decisions>
## Implementation Decisions

### Root Cause & Phase Anchor

- **D-01:** The dominant cause of Phase 3.1's ~1% allocation throughput is row-position
  misalignment between `trans_rates.csv` and the alphabetically-sorted probability-map cube
  Dinamica builds in `CreateCubeOfProbabilityMaps`. Confirmed empirically by the user via a
  manual row-reorder of the Phase 3.1 BAU × costa_peruana × 2022→2026 probability TIFs:
  with order corrected, the majority of the demanded transition cells were placed. Phase 3.3
  ships the structural fix first; downstream remediation knobs are deferred until the fix is
  in and re-measured.

### Alignment Contract — Single-Source Writer

- **D-02:** Single-source structural write inside `src/allocation.r`. Refactor
  `prepare_region_worker_inputs()` + `generate_probability_maps()` so that all four artifacts
  Dinamica reads — `trans_rates.csv` (work_dir copy), `expansion_table.csv`,
  `patcher_table.csv`, and `probability_map_dir/*.tif` — are materialised in one pass from
  one filtered, sorted data frame keyed by `id_trans`. Same row order, same row count,
  alignment by construction. No runtime assertion needed because there is no path that can
  produce a misaligned set. The Stage 4 source rate CSV on disk is unchanged — this is a
  work_dir-local filter applied at allocation entry.

- **D-03:** Drop both persistence rows (`from_val == to_val`) AND zero-rate rows
  (`Rate == 0`) from the work_dir `trans_rates.csv` before any of the four artifacts are
  written. No gaps in the `%03d_id_trans_*.tif` prefix sequence, no wasted predicts, no
  wasted TIFs. The Stage 4 source rate CSV (consumed by the Phase 3.2 cross-stage audit
  script) retains its full row set; the filter is applied only to the work_dir copy used by
  Dinamica.

- **D-04:** If any active `id_trans` in the post-filter `trans_rates.csv` has no matching
  row in `alloc_params` (no `Perc_expander` / `Mean_Patch_Size` / `Patch_Size_Variance` /
  `Patch_Isometry`), `stop()` hard with the full list of missing ids. Promote the existing
  warning at `src/allocation.r:1707` to a hard failure. Forces calibration-table
  regeneration rather than silently shipping incomplete Expander/Patcher tables.

### Saturation Diagnostic — Inline + Standalone

- **D-05:** Both surfaces ship in this phase. The allocation run writes
  `saturation_summary.csv` to `work_dir` and emits a structured `AUDIT
  stage=saturation ...` log line at the end of each region run.
  `scripts/diagnose_allocation_saturation.r` reads the same artifacts plus the Dinamica log
  and `posterior.tif` for a deeper post-hoc report. Both call the same R helpers (factor the
  metric computation into reusable functions in `src/allocation.r` or a new
  `src/saturation_diagnostics.r`).

- **D-06:** Per-transition probability-map quality metrics computed for every active
  transition:
  - **Coverage:** fraction of valid (non-NoData) cells with `prob > 0`.
  - **Distribution percentiles:** P50, P90, P95, P99, max of the probability map.
  - **Demand-vs-capacity ratio:** `(Rate × area_t)` (demanded cell count) divided by the
    count of cells with `prob ≥ P50` of that map's distribution.

- **D-07:** Spatial autocorrelation (Moran's I, patch-count proxy) is NOT computed in this
  phase. Deferred to a downstream tuning phase if the per-transition floor fails after the
  alignment fix and Patcher/Expander knob choice depends on knowing the spatial structure of
  the high-probability cells.

### Throughput Acceptance — Per-Transition Floor with Exemptions

- **D-08:** Each active transition must hit **≥90%** of its demanded cells placed, EXCEPT
  for transitions explicitly listed in a `saturation_exempt` section of config (transitions
  known to be physically capacity-limited because the probability map genuinely lacks enough
  eligible cells). The phase ships an initially-empty exempt list. If a transition is
  identified as genuinely capacity-bound during verification, it is added to the list with
  written rationale and that decision is logged. Threshold (default 0.90) and exempt list
  are both config-driven via `simulation_trans_rates_params` or a sibling key.

### Reference Scope

- **D-09:** Acceptance scope is BAU × **all Peruvian regions** × first simulation timestep
  (2022 → 2026). The planner must confirm the exact region list during research (the user
  named four regions; codebase evidence suggests at least four region labels exist
  including a `selva_andina` reference in transition model filenames, but
  `inputs/regionalization/regions.json` and `config[["reg_dir"]]` are the authoritative
  sources). Multi-scenario and multi-timestep verification is Phase 4 territory.

### Out of Scope (this phase)

- **D-10:** Post-alignment remediation paths are explicitly deferred unless the alignment
  fix alone fails to clear the per-transition floor on the reference scope:
  - Patcher parameter tuning (`Mean_Patch_Size`, `Patch_Size_Variance`, `Patch_Isometry`)
  - Expander `Perc_expander` rebalancing
  - Probability map post-processing (floor, smoothing, rescaling)
  - Reviving the commented-out monte-carlo calibration_allocation_parameters loop
    (`src/calibrate_allocation_parameters.r:73-128`)

  If post-fix evidence shows residual saturation that is not exemption-eligible, the
  appropriate knob will be selected as a follow-up plan within this phase, informed by the
  diagnostic output.

</decisions>

<specifics>
## Specific Ideas

- **Empirical confirmation:** The user manually corrected probability map row order on the
  Phase 3.1 BAU × costa_peruana × 2022 → 2026 run and observed that "the majority of
  transition cell targets were achieved". This is not a hypothesis — it is the validated
  fix direction. The planner should NOT spend research effort relitigating whether
  alignment is the cause.
- **Dinamica's alignment contract is documented inline in the submodel:**
  `dinamica/dinamica_model/evoland_ego_Submodels/CreateCubeOfProbabilityMaps.ego-decoded`
  line 3 states "Probability maps must be ordered using a prefix like `1_`, e.g.
  `1_filename.tif` according to the number of the row of the respective transition". The
  cube is built via `ListFilenames` (alphabetic sort) + `ExpandTableToUniqueKeys` on the
  transition matrix; cube layer index = position in the alphabetic file list = expected
  position in the transition matrix row sequence.
- **The current bug surface:** `src/allocation.r:2265-2316` iterates `trans_rates_dt` with
  `k = seq_len(.N)`, writes `sprintf("%03d_id_trans_%d.tif", k, id_trans)`, but line 2271
  `if (from_val == to_val || rate == 0) next` skips writing TIFs for those rows. Result:
  prefix sequence has gaps (001, 002, 003, 005, 006, ...) so the alphabetic-listing
  position no longer equals the trans_rates.csv row position.
- **The id_trans key is stable:** Phase 3.2 RESEARCH confirms `id_trans` is present in
  every cross-stage artifact (viable_transitions_lists.csv, reconciliation.rds, rate CSVs,
  trans_rates.csv, alloc_params.csv). The single-source writer should key off `id_trans`
  ascending for the work_dir artifact sort order.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets

- `prepare_region_worker_inputs()` already loads trans_rates_df and alloc_params, sorts
  each by `id_trans`, and warns on missing alloc_params entries. The single-source filter
  and the stop()-promotion (D-02, D-03, D-04) slot in here as a small, localised refactor.
- `generate_probability_maps()` already writes `%03d`-prefixed TIFs and the underlying
  loop structure is correct — it just needs to iterate a filtered data frame instead of
  one that contains skipped rows.
- `log_msg()` (`src/utils.r`) — structured logging used by all stages; reuse for the
  inline `AUDIT stage=saturation ...` line and the per-transition saturation log entries.
- `terra::rast()` / `terra::values()` / `terra::global()` — sufficient for all metrics in
  D-06 (coverage, percentiles, demand-vs-capacity); no new geospatial dependencies needed.
- `data.table` ordering and keyed lookup primitives — already used throughout
  allocation.r; appropriate for the new metric tables.

### Established Patterns

- `id_trans` as the cross-stage stable key (Phase 3.2 RESEARCH) — the single-source writer
  must key off this column for sort order, not `(from_val, to_val)` lexicographic.
- Config-driven thresholds via `get_config()` + `build_full_config()` — the saturation
  threshold and exempt list follow this pattern.
- Per-region work_dir layout `outputs/simulations/{scenario}/{year_ant}/region_{region_label}/` —
  the new `saturation_summary.csv` lives alongside the four Dinamica inputs in this
  directory.
- AUDIT log line convention from Phase 3.2 (`AUDIT stage=N scenario=S region=R ...`) —
  reuse the same prefix for the saturation line so the cross-stage audit script can pick
  it up.

### Integration Points

- The single-source writer feeds directly into `apptainer exec ... DinamicaEGO.sh
  allocation.ego` (via `run_allocation_dinamica()` → `exec_dinamica()` →
  `resolve_dinamica_launch()`). No changes to the Dinamica launch contract; alignment fix
  is purely on the artifact-write side.
- The saturation diagnostic reads the same `work_dir` that Dinamica writes
  `posterior.tif` into. The standalone script also parses the Dinamica log file under
  `logs/dinamica-{ts}.log` (see `.check_dinamica_post_run()` in `src/dinamica_utils.r`
  for the existing log-grep pattern).
- The Phase 3.2 cross-stage audit script (`scripts/audit_transition_pipeline.r`, in
  flight) reads the Stage 4 source rate CSV, NOT the work_dir filtered copy — these are
  intentionally different consumers, and D-03's work_dir-local filter must not affect
  Phase 3.2's audit results.

<deferred>
## Deferred Ideas

- **Patcher parameter tuning** (`Mean_Patch_Size`, `Patch_Size_Variance`, `Patch_Isometry`) —
  defer until post-alignment diagnostic evidence demands it. Would need spatial
  autocorrelation metrics first (also deferred).
- **Expander `Perc_expander` rebalancing** — defer; Phase 3.1 already fixed the
  percentage→fraction unit conversion (commit `4bdbd1e`), so the values are correctly
  scaled but possibly still too high; tuning is a separate decision.
- **Probability map post-processing** — floor, smoothing, rescaling, calibration to
  historical transition frequencies. Defer; structural alignment must be in place first to
  isolate the signal.
- **Reviving the monte-carlo `calibrate_allocation_parameters` pipeline**
  (commented out at `src/calibrate_allocation_parameters.r:73-128`) — defer; uses
  Dinamica-internal similarity validation that would need its own design work.
- **Spatial autocorrelation metrics** (Moran's I, patch-count proxy) for probability maps
  — defer; useful for Patcher/Expander tuning but not for alignment validation.
- **Multi-scenario / multi-timestep verification** — Phase 4 SC1 (all four scenarios × all
  regions × all timesteps); Phase 3.3 verifies BAU × all regions × first timestep only.
- **Promoting `setup_allocation_inputs()` id_trans warning to stop** — Phase 3.2 RESEARCH
  Open Question 3 deferred this to Phase 4 (end-to-end correctness).
- **Auto-detecting capacity-bound transitions and populating `saturation_exempt`
  automatically** — defer; manual curation with rationale is preferable for the first
  iteration to build operator intuition about which transitions are physics-bound vs.
  bug-bound.

</deferred>
