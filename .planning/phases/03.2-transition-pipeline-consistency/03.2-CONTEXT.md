`transition_identification.r` deduces theoretical candidates per region, `transition_feature_selection.r`
confirms statistical viability and writes the definitive viable set, `transition_modelling.r`

future rates over the viable set with scenario narrative exclusions applied as an explicit
logged filter, and `allocation.r` loads only the models whose transitions appear in the

<decisions>
## Implementation Decisions

### Year-step sequence config shape

- **D-01:** Move the year sequence to an explicit list in both config YAMLs under a new
  top-level key `simulation_year_steps`. The current hardcoded sequence
  `[2022, 2024, 2028, 2032, 2036, 2040, 2044, 2048, 2052, 2056, 2060]` is faithfully
  reproduced in `config/local_config.yaml` and `config/hpc_config.yaml`. This preserves the
  intentional 2-year first step (2022 → 2024) — which the pure-derivation alternative
  (`seq(2022, 2060, by = 4)`) would silently lose. The R code reads
  `config[["simulation_year_steps"]]` directly and does NOT attempt to derive the sequence
  from `simulation_start_year + step_length`.

### Validation contract

- **D-02:** At pipeline entry (inside `prepare_region_trans_rates()` or the earliest point
  where `simulation_year_steps` is consumed), validate three invariants and `stop()` hard
  on any failure:
  1. `simulation_year_steps[1] == simulation_start_year`
  2. `tail(simulation_year_steps, 1) == simulation_end_year`
  3. `all(diff(simulation_year_steps) > 0)`
  The error message must name which invariant failed and the concrete observed vs. expected
  values (e.g., `"simulation_year_steps ends at 2058 but simulation_end_year is 2060 — update
  one to match the other before continuing"`). Warning is NOT sufficient — the 2060 horizon
  is a hard requirement; drift must be impossible.

### Canonical anchor keys

- **D-03:** Keep `simulation_start_year` and `simulation_end_year` as canonical anchor keys
  in config. They are NOT removed and NOT derived from `simulation_year_steps`. Their role
  becomes "the assertion that `simulation_year_steps` is checked against" — duplication is
  intentional and serves as a tripwire. Any future operator who updates one without the
  other gets an immediate stop() at pipeline entry rather than a silently shifted simulation
  horizon. `step_length` (currently 4) is retained too but flagged as non-load-bearing for
  the sequence itself — it remains valid as documentation of the regular cadence and may
  still be consumed elsewhere (e.g., calibration scripts).

### Plan 03.2-01 delta required

- **D-04:** The existing Plan 03.2-01 prescribes the regular-derivation alternative
  (`unique(c(seq(start, end, by = step), end))`) which produces
  `[2022, 2026, 2030, ..., 2058, 2060]` — moving the irregularity from the start to the
  end of the sequence and breaking faithful reproduction of the hardcoded behaviour.
  Plan 01 must be replanned to apply D-01..D-03 instead. Plans 02 and 03 are unaffected.

</decisions>

<specifics>
## Specific Ideas

- The hardcoded sequence's 2-year first step (`2022 → 2024`) is semantically meaningful —
  not an artifact — and must survive the refactor. Operator has confirmed they would rather
  duplicate the list in config than risk losing the short first step via naive derivation.
- The validation must point at the specific mismatch in its error string so a fresh operator
  can fix the YAML in one round-trip without re-reading source code.

<code_context>
## Existing Code Insights

### Reusable Assets

- `get_config()` / `build_full_config()` in `src/setup.r` — already resolves YAML keys into
  a single config list; `config[["simulation_year_steps"]]` will Just Work once the YAML
  keys are added.
- `stop()` + `sprintf()` is the established error-emission pattern; mirror the message
  shape from existing stop() sites in `src/simulation_trans_rates_prep.r` (e.g., the
  forbid_pairs validation messages) for consistency.

### Established Patterns

- Config keys use snake_case at the top level of each YAML; lists use YAML inline-array
  syntax (`[2022, 2024, ...]`). Both local_config.yaml and hpc_config.yaml MUST mirror the
  same keys with identical shapes (Phase 1 convention — diverging is treated as a bug).
- Validation happens at the earliest point where the value is consumed, with a stop() that
  names the offending value — not at a separate validation phase or pre-flight (consistent
  with existing `prepare_region_trans_rates()` checks).

### Integration Points

- Downstream consumers of `year_steps` and `step_length` inside
  `simulation_trans_rates_prep.r` (the inner `run_scalar_optimization_loop()` etc.) read
  these as function parameters today. After the refactor they still receive the same
  vectors — just sourced from config rather than the hardcoded literal. No signature
  changes required downstream.

</code_context>

<deferred>
## Deferred Ideas

- Auto-deriving `simulation_year_steps` from a "schedule template" (e.g., a config block
  describing baseline-step-then-regular-cadence semantically) — over-engineered for current
  needs; the explicit list is clearer.
- Cross-validating `simulation_year_steps` against the `data_periods` calibration windows
  (e.g., to ensure `2022` aligns with the end of the most recent calibration period
  `2018_2022`) — a useful future check but out of scope for this narrow decision.
- Promoting `step_length` to a derived value (`max(diff(simulation_year_steps))` or similar)
  — defer; keeping it as an independent config key documents the regular cadence intent
  and may be read by other scripts.

</deferred>
