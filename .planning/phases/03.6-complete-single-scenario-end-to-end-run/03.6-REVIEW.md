# Phase 3.6: Code Review Report

**Reviewed:** 2026-06-25T14:09:30Z
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Reviewed the Phase 3.6 capstone changes: the D-11 explicit-schedule timestep
build, the D-05 per-region single-region decouple, the D-10 atomic raster write
helper in `src/allocation.r`, plus the new SBATCH launcher/job bodies, the
post-hoc national-mosaic assembler, the run manifest, the verifier and the
pre-flight gate.

The atomic-write helper (D-10) and the schedule-validation block (D-11) are
sound and fail-closed. The pre-flight gate, manifest verdict logic, and verifier
exit-code propagation are well constructed. The dependency-fan-out launcher is
mostly correct.

However, the **timestep-resume mechanism (D-09) is broken in two compounding
ways** and will produce silently-wrong output rather than failing loudly. The
launcher reuses `ALLOCATION_YEAR_POST_FILTER`, a variable whose driver-side
semantics are "run EXACTLY ONE timestep" (the smoke filter), to mean "resume
from this year onward." It does neither correctly: a resumed region runs a single
timestep, and that timestep's anterior is chained off the 2022 initial LULC
rather than the prior posterior. These are the two BLOCKERs below. There are also
six WARNINGs, the most important being the single-region branch returning a
region-trimmed posterior into a full-extent mask (a geometry change vs. the prior
behaviour the comment claims is a no-op).

## Critical Issues

### CR-01: Resume reruns only ONE timestep, not "from the resume year onward"

**File:** `scripts/submit_allocation_scenario.sh:133-162`, `src/allocation.r:507-534`
**Issue:**
The launcher computes `RESUME_YEAR` as the FIRST incomplete posterior year and
exports it as `ALLOCATION_YEAR_POST_FILTER` (line 158), with the stated intent
(header lines 22-27, body comment lines 153-162) that "the region resumes from
there instead of re-running completed timesteps."

But `ALLOCATION_YEAR_POST_FILTER` is consumed by `filter_allocation_timesteps()`
(`src/allocation.r:507`), which restricts the schedule to a **single** timestep:

```r
idx <- which(year_ends == year_post)   # line 517 — one index
...
list(year_starts = year_starts[idx], year_ends = year_ends[idx])  # one element
```

This is the original smoke-test "run exactly one posterior year" filter
(`scripts/submit_allocation_smoke.sh:70-73`). So a region that has completed
e.g. 2024 and 2028 but is missing 2032..2060 will run ONLY the 2032 timestep
and exit 0 ("complete"). Posterior years 2036..2060 are never produced. The
region job reports success, the afterok mosaic job launches, and the manifest
later reports INCOMPLETE — but the per-region job gave no error, so an operator
re-running the launcher just advances ONE more timestep per submission. The run
never converges to a full chain through resume.

**Fix:** Resume must select the tail of the schedule from the resume year, not a
single element. Either add a distinct "from this year onward" env var, or change
`filter_allocation_timesteps()` to keep all steps with `year_ends >= year_post`:

```r
# src/allocation.r — resume-from-year semantics (separate from single-year smoke)
idx <- which(year_ends >= year_post)
if (!length(idx)) stop(sprintf(
  "ALLOCATION_YEAR_POST_FILTER=%d is not >= any posterior year for scenario '%s'",
  year_post, scenario))
list(year_starts = year_starts[idx], year_ends = year_ends[idx])
```

Do NOT silently overload the existing single-timestep smoke filter — introduce a
separate variable (e.g. `ALLOCATION_RESUME_FROM_YEAR`) so smoke runs and resume
runs keep distinct, tested semantics. See also CR-02, which must be fixed
together.

### CR-02: Resumed timestep chains its anterior off the 2022 initial LULC, not the prior posterior

**File:** `src/allocation.r:1508`, `1543-1547`, `1577-1606`
**Issue:**
`current_lulc_path` is seeded once to the start-year LULC
(`current_lulc_path <- initial_lulc_file[1]`, line 1508) and is only advanced
inside the timestep loop via each timestep's return value (line 1588). When
`filter_allocation_timesteps()` subsets the schedule for a resume/filter run, the
loop starts with `current_lulc_path` STILL pointing at the 2022 initial raster —
there is no logic to seed it from the previous completed posterior.

So even after CR-01 is fixed (or for any single-timestep filter run that is not
the first timestep), the resumed timestep's per-region anterior is built by
`prepare_region_worker_inputs()` masking the **2022** LULC
(`terra::mask(current_lulc, ...)`, line 866), not the year N-1 posterior. The
chain restarts from 2022 state for the resumed step, corrupting the trajectory
(every posterior after a resume boundary reflects 2022→N transitions instead of
(N-1)→N).

**Fix:** When a resume/filter year is set, seed `current_lulc_path` from the
prior completed posterior before the loop. With the per-region decouple (D-05)
the prior state is `region_<suffix>/posterior.tif` for the immediately-preceding
posterior year; resolve and assign it:

```r
# after building year_starts/year_ends (post-filter), if resuming:
if (resume_index > 1L) {
  prev_year_post <- year_ends_full[resume_index - 1L]
  current_lulc_path <- file.path(
    sim_dir, as.character(prev_year_post),
    paste0("region_", region_suffix), "posterior.tif"
  )
  if (!file.exists(current_lulc_path))
    stop(sprintf("resume: prior posterior missing: %s", current_lulc_path))
}
```

Note this also interacts with CR-AnteriorExtent (WR-01): the prior single-region
posterior is region-trimmed, so the masking-against-full-grid concern applies to
the chained anterior as well. CR-01, CR-02 and WR-01 should be designed and
verified as one unit.

## Warnings

### WR-01: Single-region branch returns a region-trimmed posterior where the prior code returned a full-extent raster

**File:** `src/allocation.r:1868-1875` (vs. base 1796-1814)
**Issue:**
The new single-region branch returns `posterior_paths[[1]]`
(`region_<suffix>/posterior.tif`), which is `terra::trim()`-ed to the region's
bounding box (anterior is trimmed at line 872; the posterior inherits that
extent). The BASE code, even for one region, ran `terra::extend(r, full_extent)`
before returning `posterior_<year>.tif` — a FULL national-extent raster. So
`current_lulc_path` for the next timestep changes from a full-grid raster to a
region-bbox raster.

The next timestep then does `terra::mask(current_lulc, region_rast, ...)`
(line 866) where `region_rast` is the full national grid. `terra::mask` operates
on the intersection/alignment of geometries; feeding a smaller-extent raster
against the full-extent mask is not obviously the "no-op" the comment
(lines 1862-1864) asserts — it can drop the padding cells or mis-align if the
trimmed extent does not snap to the mask grid. This is a behaviour change vs. the
byte-comparable path the assembler claims to preserve, and it directly affects
the resume chain (CR-02).

**Fix:** Verify with a 2-timestep single-region run that
`region_<suffix>/posterior.tif` (trimmed) re-masked against the full
`region_rast` reproduces the same cells as the prior full-extent path. If it does
not, extend the returned posterior to the full extent before returning (matching
the prior chain geometry), or document and test the trim/mask round-trip
explicitly. Do not rely on the comment's assertion without an actual round-trip
check.

### WR-02: Already-complete re-run permanently skips national mosaic assembly

**File:** `scripts/submit_allocation_scenario.sh:144-149`, `179-184`
**Issue:**
If all per-region posteriors exist but the national `posterior_<year>.tif`
mosaics were never produced (e.g. a prior run's region jobs succeeded but the
afterok mosaic job failed, was cancelled, or the dependency was released on a
partial failure), re-running the launcher finds every region "complete"
(lines 144-148), submits zero region jobs, so `ID_LIST` is empty and the mosaic
job is explicitly skipped (lines 181-184). The national mosaics stay missing
forever via this path; the manifest will report INCOMPLETE with no automatic
remedy. The launcher's resume logic only keys on per-region posteriors, never on
mosaic presence.

**Fix:** Make mosaic-assembly submission independent of whether region jobs were
submitted. When `ID_LIST` is empty but regions are complete, still submit the
mosaic job (without the afterok dependency) so missing national mosaics are
filled:

```bash
if [ -z "$ID_LIST" ]; then
    MOSAIC_ID=$(sbatch --parsable --export=ALL,ALLOC_SCENARIO="$SCENARIO" "$MOSAIC_JOB")
else
    MOSAIC_ID=$(sbatch --parsable --dependency=afterok:"$ID_LIST" \
        --export=ALL,ALLOC_SCENARIO="$SCENARIO" "$MOSAIC_JOB")
fi
```

(The assembler already skips years whose region posteriors are incomplete, so an
unconditional submit is safe.)

### WR-03: Manifest demand soft-check key mismatch silently zeroes every observed class

**File:** `scripts/run_manifest.r:341-345`, `403-416`
**Issue:**
`final_year_class_area` is keyed by `as.character(cell$freq$value)` — the integer
LULC code from `terra::freq()` (e.g. "3"). The demand lookup at line 416 does
`obs <- final_year_class_area[[cls]]` where `cls` is read from the demand table's
class column (line 411), which the column-detection at line 403 also allows to be
a name column (`"lulc"`, `"class"`, `"lulc_class"`). If the demand CSV keys by
class NAME rather than integer code, every lookup misses, `obs_frac` is forced to
0, and a demand mismatch is reported for every class — or, if the deviation is
under tolerance by coincidence, silently passes. The check is report-only (never
gates the verdict per D-08b), so this is a correctness-of-warning issue, not a
verdict bug, but it makes the plausibility audit unreliable.

**Fix:** Normalise both sides to the same key space before comparing (map class
names to integer codes via the project's `class_name_to_value`, or require the
demand table's class column to be integer codes and validate it). At minimum log
when zero observed classes match any demand row so the mismatch is not silent:

```r
matched <- sum(vapply(as.character(demand_df[[class_col]]),
  function(c) !is.null(final_year_class_area[[c]]), logical(1)))
if (matched == 0L) log_msg(sprintf(
  "AUDIT stage=plausibility scenario=%s status=demand_key_space_mismatch ...", scenario))
```

### WR-04: Submit scripts run setup/activation under `set +e` without checking failure

**File:** `scripts/submit_allocation_scenario.sh:29,66-67`; `scripts/submit_allocation_region.sh:43,86-87`; `scripts/submit_assemble_mosaic.sh:29,62-63`
**Issue:**
These scripts use `set -uo pipefail` (no `-e`). `setup_common_env` and
`activate_env "$ENV_PATH"` are called with no return-code check (unlike the
`verify_rscript` call right after, which IS checked via `$?`). If environment
activation partially fails (e.g. micromamba activate errors but the function
returns non-zero), execution continues; `verify_rscript` may then still find a
stale on-PATH Rscript or the wrong env, and the job proceeds against the wrong
interpreter. For the launcher this is worse: a failed activation followed by a
working fallback Rscript could probe regions/schedule from a different
environment than the jobs will run in.

**Fix:** Check the return code of activation explicitly, or add `set -e` for the
setup section:

```bash
setup_common_env || { echo "ERROR: setup_common_env failed" >&2; exit 1; }
activate_env "$ENV_PATH" || { echo "ERROR: activate_env failed for $ENV_PATH" >&2; exit 1; }
```

### WR-05: `length(region_inputs) == 1` heuristic silently suppresses the national mosaic for a genuine single-region national run

**File:** `src/allocation.r:1868`
**Issue:**
The decision to skip the national mosaic write is keyed purely on
`length(region_inputs) == 1` (the comment at 1866-1867 notes this is to avoid a
new env var). But this conflates "per-region filtered job" with "a national run
whose `regions.json` legitimately declares exactly one region." In the latter
case an unfiltered national run would now produce NO `posterior_<year>.tif` and
return the region-trimmed posterior as the chained state — a silent behaviour
change with no national output, depending entirely on the post-hoc assembler
being run. There is no assertion that `ALLOCATION_REGION_FILTER` was actually set.

**Fix:** Gate the branch on the actual intent — that a region filter is active —
rather than inferring it from region count:

```r
region_filtered <- nzchar(Sys.getenv("ALLOCATION_REGION_FILTER", unset = ""))
if (region_filtered && length(region_inputs) == 1L) { ... single-region path ... }
```

so a genuine one-region national run still writes (and chains on) the national
mosaic.

### WR-06: `write_raster_atomic` leaves orphaned `.tmp.tif` on rename failure and ignores GDAL sidecars

**File:** `src/allocation.r:46-70`
**Issue:**
On `file.rename` failure (cross-filesystem move, or target exists on a non-POSIX
fs) the helper `stop()`s (good, fail-closed) but leaves the `.tmp.tif` behind.
Worse, the D-09 resume scan in the launcher globs only `posterior.tif`, so an
orphaned `region_<suffix>/posterior.tif.tmp.tif` is harmless — but an orphaned
`anterior.tif.tmp.tif` accumulates. Additionally, if `terra::writeRaster`
produces a GDAL sidecar (e.g. `*.tif.aux.xml`) for the temp path, only the
`.tmp.tif` is renamed; the sidecar keeps the `.tmp.tif.aux.xml` name and is
orphaned/mis-referenced.

**Fix:** Clean up the temp on rename failure before `stop()`, and account for any
sidecar:

```r
if (!file.rename(tmp_path, final_path)) {
  unlink(tmp_path)
  stop(sprintf("Atomic raster write failed: could not rename '%s' -> '%s'",
               tmp_path, final_path))
}
```

LZW INT2U GeoTIFFs with no stats typically emit no sidecar, so this is low-risk,
but the unlink-on-failure is cheap insurance.

## Info

### IN-01: `step_length` read but deliberately unused — remove or comment at the read site

**File:** `src/allocation.r:1492`
**Issue:** `step_length <- config[["step_length"]]` is now dead (the schedule is
built from `simulation_year_steps`; the comment at 1517-1519 calls it an "unused
fallback" but it is never referenced). A future reader may wire it back in by
mistake.
**Fix:** Drop the assignment, or annotate it inline as intentionally retained and
unused so it is not accidentally reused for pair construction.

### IN-02: Assembler matches the initial LULC file by year-substring regex and silently takes `[1]`

**File:** `scripts/assemble_national_mosaic.r:179-186`
**Issue:** `lulc_files[grepl(as.character(start_year), lulc_files)]` treats the
year as a regex against the full path and silently uses `initial_lulc_file[1]` if
several match. A path component containing the year digits elsewhere could select
the wrong national extent. (Pre-existing pattern in `src/allocation.r:1499`, but
this is new code in the assembler.)
**Fix:** Anchor the match to the filename and assert a unique result:

```r
hits <- lulc_files[grepl(sprintf("(^|[^0-9])%d([^0-9]|$)", start_year),
                          basename(lulc_files))]
if (length(hits) != 1L) stop("expected exactly one initial-LULC raster, got ",
                             length(hits))
```

### IN-03: Manifest casts posterior years to integer; assembler does not — keep consistent

**File:** `scripts/assemble_national_mosaic.r:138` vs `scripts/run_manifest.r:151`
**Issue:** `run_manifest.r` uses `as.integer(tail(year_steps, -1))`; the
assembler uses the raw `tail(year_steps, -1)` and relies on `sprintf("%d", ...)`
accepting whole-number doubles. It works for integral years but the divergence is
a latent foot-gun if a non-integral boundary ever slips into the config.
**Fix:** Use `as.integer(tail(year_steps, -1))` in the assembler too, matching the
manifest.

### IN-04: Verifier CSV-path extraction is brittle vs. the manifest log format

**File:** `scripts/verify_allocation_run.sh:87-88`
**Issue:** The manifest CSV path is recovered by grepping
`Wrote run manifest CSV.*: .*run_manifest\.csv` and `sed`-stripping everything up
to the last `: `. If the manifest's "Wrote run manifest CSV (N rows): <path>"
wording ever changes, or the path itself contains `: `, the extraction breaks
silently (the `|| true` swallows it) and only the path display is lost — verdict
and exit code are unaffected. Low impact.
**Fix:** Have `run_manifest.r` emit a single machine-stable line, e.g.
`STATE manifest csv=<path>`, and grep that exact key instead of parsing prose.
