# Phase 3.2: Transition Pipeline Consistency - Research

**Researched:** 2026-05-22
**Domain:** R pipeline data-flow; transition set consistency across five pipeline stages
**Confidence:** HIGH (all findings verified by reading source files directly)

---

## Summary

Phase 3.2 hardens the end-to-end flow of "viable transitions" through five pipeline stages. A detailed read of all five source files reveals that the pipeline already has substantial consistency infrastructure — the viable_transitions_lists.csv is the shared source of truth used by stages 2 through 5 — but there are specific gaps, silent drop points, and missing audit hooks that allow the transition set to drift undetected.

The central artifact is `viable_transitions_lists.csv`, written by `transition_identification.r` and read by both `transition_feature_selection.r`, `transition_modelling.r` (via reconciliation), and `simulation_trans_rates_prep.r`. The allocation stage (`allocation.r`) reads the per-scenario/per-timestep CSV files output by `simulation_trans_rates_prep.r`, not the viable_transitions_lists.csv directly. The Phase 3.1 fix to `load_allocation_models()` already filters models to `active_transitions` (from the rate CSV), which closes the over-loading gap at stage 5.

The remaining gaps are: (a) no enforcement that `transition_feature_selection.r` sees exactly the same transition set as `transition_identification.r` wrote — feature selection loads only `whole_map` rows with a non-NA `rate_{period}` column, which is correct but not audited; (b) `transition_modelling.r`'s reconciliation already documents FS failures and missing models, but does not stop or warn when a viable transition has no model; (c) `simulation_trans_rates_prep.r`'s only transition exclusion mechanism is the hard-coded `mining` prohibition and unmodelled transitions from the reconciliation file — there are no scenario-narrative exclusions currently configured; (d) there is no cross-stage audit script.

**Primary recommendation:** Add assertion-layer guards at each stage boundary that compare the transition set entering vs. leaving each stage, emit a logged audit table, and stop (not warn) when the sets diverge without a documented reason.

### id_trans: The Pipeline's Stable Transition Identifier

`id_trans` is assigned in `transition_identification.r` as a sequential integer per unique (From., To.) pair (persistence rows get NA). It propagates through:
- viable_transitions_lists.csv (column `id_trans`)
- transition_modelling_reconciliation_{period}.rds (column `id_trans`)
- rate CSVs output by stage 4 (column `id_trans`)
- trans_rates.csv in each region work_dir (column `id_trans`)
- alloc_params.csv (column `id_trans`) — the expansion/patcher calibration table

`id_trans` is the safest cross-stage join key because it is stable, integer-typed, and already present in all relevant artifacts.

## Architecture Patterns

### Stage 1: transition_identification.r — What It Outputs

`transition_identification.r` computes transition crosstabs from historic LULC rasters for each calibration period. It produces one primary output:

**viable_transitions_lists.csv** — columns: `region_name`, `from_lulc`, `to_lulc`, `From.`, `To.`, `id_trans`, `rate_{period}` (one column per calibration period).

- Rows with `from_lulc == to_lulc` are persistence rows (`id_trans = NA`).
- Off-diagonal rows (real transitions) have integer `id_trans`.
- `region_name` is either `"whole_map"` (full-extent rates) or a region label (e.g., `"costa_peruana"`) when `regionalization = TRUE`.
- Only transitions observed in the historic data (non-zero crosstab entries) get rows — a transition that never occurred gets no row.

**Key finding:** The viable set entering stage 2 is defined by: rows in viable_transitions_lists.csv where `region_name == "whole_map"`, `from_lulc != to_lulc`, and `!is.na(rate_{period})`. This filter is applied identically in both `transition_feature_selection.r` (line 117-121) and `reconcile_period_transitions()` in `transition_modelling.r` (lines 466-481). So stages 1→2 and 1→3 share the same implicit filter. There is no documented audit log confirming the counts match.

### Stage 2: transition_feature_selection.r — How It Reads Stage 1

```r
# [VERIFIED: src/transition_feature_selection.r lines 115-121]
vt_csv <- read.csv(config[["viable_transitions_lists"]])
rate_col <- paste0("rate_", period)
transitions_info <- vt_csv[
  vt_csv$region_name == "whole_map" &
    vt_csv$from_lulc != vt_csv$to_lulc &
    !is.na(vt_csv[[rate_col]]),
]
transitions_info$Trans_name <- paste(
  transitions_info$from_lulc,
  transitions_info$to_lulc,
  sep = "-"
)
```

The function processes all transitions from the whole_map slice. It then expands into a `task_grid` of transition × region combinations for parallel processing. The output is saved as per-period RDS files (`transition_feature_selection_summary_{period}.rds` for successes, `feature_selection_failed_{period}.rds` for failures).

**Gaps identified at Stage 2 boundary:**
- The function only logs the count of viable transitions loaded; there is no assertion comparing it against stage 1's expected count.
- Transitions that fail feature selection (status: `"insufficient_observations"`, `"insufficient_transitions"`, `"collinearity_filtering_failed"`, `"grrf_failed"`) are saved to the failed RDS but this does not stop stage 3 from proceeding.
- The `transition_feature_selection` orchestrator references `final_summary` on line 63 but `final_summary` is never assigned inside the function — this is a latent bug that will cause an error when the function reaches its return statement.

### Stage 3: transition_modelling.r — Reconciliation Infrastructure

`transition_modelling.r` has a `reconcile_period_transitions()` function (lines 431-651) that is the most complete cross-stage audit currently in the pipeline. It:

1. Loads viable_transitions_lists.csv and computes `expected_transitions` (same whole_map filter as stage 2).
2. Cross-joins with `region_names` to get `expected_pairs` (all transition × region combinations).
3. Left-joins against FS success and failure RDS files.
4. Produces a reconciliation tibble with `fs_status` per pair: `"success"`, `"failed"`, or `"missing"`.
5. After training, updates with `model_status`: `"success"`, `"error"`, `"skipped_no_predictors"`, `"not_attempted_fs_failed"`, `"not_attempted_fs_missing"`, `"missing_no_file"`.
6. Writes reconciliation_{period}.csv and .rds.

**Key finding:** `model_single_transition()` (line 1214) checks if a model file exists and skips if `refresh_cache = FALSE`. The reconciliation's `model_status = "success"` is set when `model_file_exists = TRUE` (line 1133), not when the model was actually trained in this run. This means if a model file exists from a previous run, it is counted as success even if it was trained on a different FS output. **This is a correctness gap** — cached model files may not correspond to the current viable_transitions_lists.csv.

**Key finding:** `load_unmodelled_transitions()` (lines 22-46) reads the reconciliation file to identify which transitions have `model_status != "success"`. This reconciliation output is then used by stage 4 to populate `forbid_pairs_df`. This is the correct mechanism for propagating model failures downstream.

### Stage 4: simulation_trans_rates_prep.r — Transition Exclusion Mechanisms

Stage 4 has two exclusion mechanisms for transitions:

**Mechanism 1: Hard-coded mining prohibition**
```r
# [VERIFIED: src/simulation_trans_rates_prep.r lines 243-248]
forbid_pairs_df <- tidyr::expand_grid(
  region_name = NA_character_,
  From = "mining",
  To = setdiff(lulcs_global, "mining")
)
```
All transitions FROM mining to any other class are forbidden globally. This is hardcoded, not config-driven, and not logged as a filter.

**Mechanism 2: Non-modelled transitions from reconciliation**
```r
# [VERIFIED: src/simulation_trans_rates_prep.r lines 250-259]
unmodelled_df <- load_unmodelled_transitions(config)
forbid_pairs_df <- dplyr::bind_rows(forbid_pairs_df, unmodelled_df) %>% dplyr::distinct()
```
Transitions without fitted models are added to `forbid_pairs_df` and forced to zero rate via `build_mats()`.

**Gaps identified at Stage 4:**
- The mining prohibition is a scenario-agnostic hard constraint applied via `build_mats()`. It is not documented in the config and is not scenario-specific.
- `forbid_pairs_df` uses `From`/`To` (class_name), while the rate CSV uses `From*`/`To*` (numeric LULC values). The mapping via `class_to_value` in `optimize_region_scenario()` is correct but introduces a translation step that could silently fail if class names change.
- The rate CSV output filters using `filter(!is.na(id_trans))` (line 879) to remove persistence rows. This means only transitions with an `id_trans` from viable_transitions_lists.csv appear in the output. **This is correct but not verified against the input count** — no log line states "X transitions entered, Y transitions in output, Z excluded by forbidden list".
- Year steps are hardcoded (lines 297-310: `c(2022, 2024, 2028, 2032, ...)`) instead of derived from `config[["simulation_start_year"]]` and `config[["step_length"]]`. This is a separate fragility.
- Scalars are hardcoded (line 1286: `scalars <- c(1.0, seq(3.0, 9.0, by = 2))`) instead of read from `config[["simulation_trans_rates_params"]][["scale_factor"]]`.

**What "scenario narrative exclusions" currently exist:** None that are scenario-specific. The only scenario-varying behavior is through `df_target_run` (demand targets differ by scenario) and `df_shape_run` (trajectory shapes differ by scenario). The `forbid_pairs_df` is identical across all scenarios.

### Stage 5: allocation.r — How It Links to Stage 4

The active transition set for allocation is derived from the rate CSV:
```r
# [VERIFIED: src/allocation.r lines 691-708, prepare_region_worker_inputs()]
csv_path <- file.path(config[["trans_rate_table_dir"]], ..., paste0(scenario, "-", region_label, "-trans_rates-", year_ant, ".csv"))
df <- utils::read.csv(csv_path, check.names = FALSE)
active_transitions <- data.table(from_val = as.integer(df[["From*"]]), to_val = as.integer(df[["To*"]]))
```

The Phase 3.1 fix (`load_allocation_models()` filtered by `active_key`) ensures models are loaded only for transitions in the rate CSV. The `generate_probability_maps()` function merges `models_list` with `trans_rates_df` by `(from_val, to_val)` (lines 1935-1942), so only model × rate row intersections are predicted. Missing models emit a warning (lines 1944-1957) rather than stopping.

**Gap at Stage 5:** The merge between models and rates uses `all.x = FALSE`, meaning unmatched models are silently dropped. The warning about missing models (in rates but not in models) is a warning, not a stop. For the Success Criterion "model count equals active-rate-table row count", this is not enforced — it is only approximated.

## Common Pitfalls

### Pitfall 1: Stage Boundary Assumes Shared Filter Logic — Never Verified

**What goes wrong:** Stages 2, 3, and 4 all apply the same `whole_map` + `!is.na(rate_{period})` filter to viable_transitions_lists.csv independently. If transition_identification.r is re-run with different parameters and produces a new CSV, stages 2/3/4 pick up the new CSV but may have cached results (FS RDS files, model .qs files) from the old run. The reconciliation in stage 3 will mark cached models as "success" even if they no longer correspond to the current viable set.

**Prevention:** Add a version hash or row-count sentinel to viable_transitions_lists.csv; check it at the start of each downstream stage.

### Pitfall 2: Mining Hard-Code Is Global, Not Logged

**What goes wrong:** The mining prohibition in `simulation_trans_rates_prep.r` applies to all scenarios equally and is not documented in any log or config. An operator inspecting a scenario run will not see evidence of this exclusion.

**Prevention:** Log `forbid_pairs_df` row counts at the start of `optimize_region_scenario()`. Move the mining prohibition to config (`simulation_trans_rates_params.forbidden_from_classes: ["mining"]`).

### Pitfall 3: Reconciliation "success" Based on File Existence, Not Current Run

**What goes wrong:** `reconcile_period_transitions()` checks `model_file_exists = file.exists(model_path)`. A model trained on an older viable_transitions_lists.csv will still pass this check.

**Prevention:** Add an `id_trans` cross-check: verify that the model's path (which encodes `trans_name`) corresponds to a `trans_name` in the current reconciliation's `expected_transitions`. This is already structurally possible since `reconcile_period_transitions()` has both.

### Pitfall 4: Stage 4 Hardcoded Year Steps and Scalars

**What goes wrong:** `year_steps` (lines 297-310) and `scalars` (line 1286) are hardcoded, not read from config. Running the simulation for a different time horizon or wanting a different scalar set requires editing source code.

**Prevention:** Read from config keys: `config[["simulation_start_year"]]`, `config[["simulation_end_year"]]`, `config[["step_length"]]`, `config[["simulation_trans_rates_params"]][["scale_factor"]]`.

### Pitfall 5: `final_summary` Not Assigned in `transition_feature_selection()`

**What goes wrong:** Line 63 of `transition_feature_selection.r` returns `final_summary`, but `final_summary` is never assigned inside the function. This will crash with "object 'final_summary' not found" when the function reaches its return statement.

**Prevention:** Either remove the `return(final_summary)` call or aggregate the per-period results inside the `purrr::map()` call and assign them to `final_summary`.

### Pitfall 6: alloc_params.csv id_trans May Not Align with Current Rate CSV

**What goes wrong:** `setup_allocation_inputs()` (lines 1697-1715) subsets `alloc_params` by `id_trans %in% trans_rates_df[["id_trans"]]` and warns when trans_rates_df has `id_trans` values not in alloc_params. If the calibration control table was built with an older id_trans assignment, this mismatch will produce silent partial expansion/patcher tables.

**Prevention:** The warning is already in place; promote it to a stop for the active scenario × region run.

## Specific Mismatches to Resolve

### Mismatch 1: No Audit Log at Stage 1 → 2 Boundary (Success Criterion 1)

**Current state:** `transition_identification.r` writes viable_transitions_lists.csv with N rows; `transition_feature_selection.r` reads it and logs "Loaded X viable transitions for period P" (line 128). There is no assertion that X matches the expected count, and no downstream stage verifies that it is reading the same CSV that was written.

**Required fix:** Add a pre-flight check at the start of `transition_feature_selection()` that reads viable_transitions_lists.csv, counts expected transitions for the period, and logs a structured message: `AUDIT stage=1->2 period=P whole_map_transitions=N`.

### Mismatch 2: Feature Selection Failures Are Not Surfaced to Stage 3 Caller (Success Criterion 2)

**Current state:** When FS fails for a transition, `model_single_transition()` in stage 3 skips training (model_status = "not_attempted_fs_failed" or "not_attempted_fs_missing"). These are logged in the reconciliation CSV but do not trigger a stop or structured warning visible to the operator at stage 3 entry.

**Required fix:** At the start of `perform_transition_modelling()`, after calling `reconcile_period_transitions()`, log a structured summary: `AUDIT stage=2->3 period=P expected=N fs_success=M fs_failed=K fs_missing=J`. If `(K + J) > 0`, emit a warning with the list of affected transitions.

### Mismatch 3: Scenario Narrative Exclusions Are Implicit (Success Criterion 3)

**Current state:** No scenario-specific transition exclusions exist in config. The only exclusions are the global mining prohibition (hardcoded) and unmodelled transitions (from reconciliation RDS). The Success Criterion requires that "scenario narrative exclusions are applied as a documented, explicit filter" — but no such filter is implemented yet for the current Peru project.

**Required interpretation:** Either (a) there are genuinely no scenario-specific exclusions needed for this project (in which case the criterion is satisfied by documenting that the only exclusions are mining + unmodelled), or (b) the criterion anticipates future scenario-specific exclusions that should be config-driven.

**Recommended approach:** Add a config key `simulation_trans_rates_params.scenario_narrative_exclusions` (a list of `{scenario, from_class, to_class}` records, currently empty) and add code to populate `forbid_pairs_df` from it. This satisfies the criterion even when the list is empty, because the exclusion mechanism is explicit and logged.

### Mismatch 4: Rate CSV Row Count Not Verified Against Viable Set (Success Criteria 3+4)

**Current state:** `optimize_region_scenario()` filters persistence rows with `filter(!is.na(id_trans))` before writing the rate CSV. But there is no log line stating "viable set had N transitions; rate CSV has M rows; K excluded by forbidden list".

**Required fix:** After building `rate_df` for each timestep, log: `AUDIT stage=4 scenario=S region=R timestep=T viable_input=N forbidden_excluded=K rate_csv_rows=M`.

The per-region viable input count is available as `nrow(df_trans_source[df_trans_source$region_name == r, ])` where `df_trans_source` is a parameter of `run_scalar_optimization_loop()`. Compute `n_viable_input` before the inner timestep loop, then use it in the AUDIT log inside the loop.

### Mismatch 5: Cross-Stage Audit Script Does Not Exist (Success Criterion 5)

**Current state:** No audit script exists. The reconciliation CSV from stage 3 is the closest artifact but covers only stages 1-3 and does not extend to stage 4 (rate counts) or stage 5 (model load counts).

**Required fix:** Write `scripts/audit_transition_pipeline.r` (or equivalent) that:
1. Loads viable_transitions_lists.csv; counts whole_map transitions per period.
2. Loads stage 2 feature selection summary RDS; counts rows with `status == "success"` for the reference region.
3. Loads stage 3 reconciliation RDS; counts model_status per period × region.
4. Scans stage 4 output directory for one reference scenario × region × timestep; counts rate CSV rows.
5. Emits a structured table comparing N at each stage and flags divergences.

## Open Questions (RESOLVED)

1. **Do scenario-narrative exclusions exist for this project?**
   - What we know: No scenario-specific transition exclusions are coded anywhere in current source.
   - What's unclear: Whether the Success Criterion implies future exclusions or expects existing ones.
   - **RESOLVED:** No scenario-specific exclusions are needed for the current Peru project. SC-3 is satisfied by moving the mining prohibition to `simulation_trans_rates_params.forbidden_from_classes: ["mining"]` in config. This makes the exclusion mechanism explicit, config-driven, and logged — the list is empty for scenario-specific exclusions, which is a documented, valid state. No additional scenario narrative exclusion mechanism is required for this phase.

2. **Should stage boundary violations stop execution or warn?**
   - What we know: Current code generally warns (not stops) on transition mismatches.
   - What's unclear: Whether a planning run should be aborted if the viable set shrank between stages.
   - **RESOLVED:** Warn by default at stage 2→3 (FS failures are expected and documented). Stop at stage 5 only (missing model for a rate-table row is a hard error because allocation cannot proceed without a probability map for that transition). No `strict_transition_audit` config flag is needed for this phase — the stop/warn split is fixed: stage 5 stops, all earlier stages warn.

3. **Does the alloc_params.csv id_trans alignment need fixing?**
   - What we know: `setup_allocation_inputs()` already warns when trans_rates_df has id_trans values missing from alloc_params. The warn-not-stop approach may silently produce incomplete expansion/patcher tables.
   - **RESOLVED:** Out of scope for Phase 3.2. The existing warning is sufficient for now. Promoting to stop is deferred to Phase 4 (PERF / end-to-end correctness). Phase 3.2 plans do not touch `setup_allocation_inputs()`.
