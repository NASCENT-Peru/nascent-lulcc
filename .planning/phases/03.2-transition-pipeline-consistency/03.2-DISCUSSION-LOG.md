## Concern raised by user

> "The plan assumes that the simulation years can be derived exactly from the start and end
> date and step length but this is not perfect which is why there was a hard coded sequence:
> `year_steps` in `simulation_trans_rates_prep.r` is hardcoded as `c(2022, 2024, 2028, ...)`.
> I want to avoid hard coding but having these details in the configs but I want to ensure
> that the target end year is reached (2060)."

Verified inline: `src/simulation_trans_rates_prep.r:297-309` contains the hardcoded
`[2022, 2024, 2028, 2032, 2036, 2040, 2044, 2048, 2052, 2056, 2060]` vector with a 2-year
first step then regular 4-year steps. The currently-planned fix in Plan 03.2-01 uses
`unique(c(seq(2022, 2060, by=4), 2060))` which produces
`[2022, 2026, 2030, ..., 2058, 2060]` — moves the irregularity from start to end of the
sequence, silently changing simulation behaviour.

## Discussion

hardcoding remains?
