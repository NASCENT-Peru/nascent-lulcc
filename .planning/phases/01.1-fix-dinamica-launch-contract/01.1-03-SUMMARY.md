## Open Issues

### Open Issue 1 — DinamicaConsole crashes with `std::exception` in the rebuilt `.sif` regardless of `.ego` content

**Severity:** Blocks INFRA-01 SC3 (live smoke exit 0) and MEM-06 SC5 (smoke fixture exercises launcher).
**Status:** Diagnosed but not fixed in Phase 1.1 scope.

**Evidence:**
- `DinamicaConsole` (no args, no env) → `std::exception` exit 0
- `bin/DinamicaEGO.sh /abs/path/smoketest.ego` → same
- `bin/DinamicaEGO.sh /tmp/allocation.ego` (production fixture) → same
- `bin/DinamicaEGO.sh /abs/path/...` invoked via absolute path (rules out relative `BIN_PATH`) → same
- `bin/DinamicaEGO.sh` (no args, GUI mode) → loads `JavaBinding/Base/Dinamica/PrimPlugin/ImagePlugin/CalibrationPlugin/SimulationPlugin` successfully → hangs on missing DISPLAY (expected)
- All probes were run inside `apptainer shell` with `--home` and `--env` matching the smoke-test launch arguments.

**Hypothesis (REFINED after operator-side ldd/LD_DEBUG diagnostic, 2026-05-17):** The original library-compat hypothesis is **FALSIFIED**. Operator-side diagnostic inside the `.sif`:
- `ldd /opt/dinamica/usr/bin/DinamicaConsole` → zero "not found" entries; all libraries (libBase, libDinamica, plugin set, libstdc++, libpython3.12, libc, libm) resolve cleanly
- `strings | grep ^GLIBC_` → binary needs up to glibc 2.34; system provides 2.39 (Ubuntu Noble 24.04)
- `LD_DEBUG=files DinamicaConsole` → loader output ends with `calling fini:` on every loaded library and exits 0, meaning the loader successfully loaded all libraries; the binary then ran briefly and threw a C++ exception during init; the `fini` phase indicates clean runtime teardown after the exception was caught

So the bug is NOT library compat. DinamicaConsole loads all its dependencies fine. The `std::exception` is thrown by Dinamica's own startup code AFTER all libraries are mapped. Likely candidates:
- A `Data/` subtree the AppImage `--appimage-extract` step dropped (or the `cp -a squashfs-root/. .` step's `rm -rf squashfs-root DinamicaEGO.AppImage` deleted some non-squashfs side asset)
- An embedded Python module (`libpython3.12.so.1.0` is mapped — Dinamica calls into Python at startup) that's missing from the sys.path the AppImage expects
- A Qt / GDAL data file expected at a path the wrapper doesn't seed (the wrapper sets `DINAMICA_EGO_8_GDAL_DATA` to a default `${BIN_PATH}/Data/GDAL` — verify that subtree was preserved from the AppImage extract)
- A registry / config key not in `.dinamica_ego_8.conf` that Dinamica treats as fatal-if-missing

**Next diagnostic step (for gap-closure phase):** Don't chase library compat. Instead:
1. `ls -R /opt/dinamica/usr/bin/Data/` inside the `.sif` — confirm GDAL data tree is intact
2. Look for any env var named `DINAMICA_EGO_8_*` referenced by `strings /opt/dinamica/usr/bin/DinamicaConsole | grep -i dinamica_ego_8 | sort -u` — we may be missing one
3. `strace -f -e openat /opt/dinamica/usr/bin/DinamicaConsole 2>&1 | tail -50` — see which files DinamicaConsole tries to read just before the exception
4. Compare against a fresh extract of the AppImage in a vanilla container (or on a workstation) to see what `cp -a squashfs-root/. . && rm -rf squashfs-root DinamicaEGO.AppImage` may have lost

If still stuck after step 4, pin a different AppImage version and rebuild — or escalate to upstream `ethzplus/rocker-geospatial-dinamica` maintainers (the upstream Dockerfile shape we ported was presumed working).

**Out of Phase 1.1 scope because:** Phase 1.1's documented scope was launch-contract repair (G1–G7), not Dinamica install correctness. Pitfall 5 in RESEARCH.md anticipated a fixture-format question; the binary-compat question is adjacent but distinct.

### A1 — Refined

Original A1: "no-op `.ego-decoded` round-tripped through `process_dinamica_script()` produces a `.ego` that DinamicaConsole accepts." Falsified specifically: a fixture with ZERO `Calculate(R|Python)Expression` blocks round-trips as a literal text copy that DinamicaConsole rejects. **Refined A1:** "fixture round-trip is valid IFF source contains ≥1 Calculate*Expression block." This is a new pattern documented above.

### Pitfall 5 — Partially Resolved

- Format-side (text vs binary): the round-trip produces text-with-base64-encoded-chunks that production accepts; an "empty" round-trip does NOT (A1 refinement above).
- Runtime-side (DinamicaConsole accepts the file): UNVALIDATED — superseded by Open Issue 1.
