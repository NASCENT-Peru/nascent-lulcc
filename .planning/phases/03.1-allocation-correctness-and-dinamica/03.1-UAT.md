## Test Sessions

### Session 1 — 2026-05-25 HPC run (initial — FAILED SC3)

**Job:** `submit_allocation_dinamica_only.sh`, BAU × costa_peruana × 2026. Elapsed 489 s. Exit 0.
Dinamica executed but **0 cells changed** — posterior pixel-identical to anterior despite
different md5 hashes (metadata-only difference).

Root cause: `lulc_demand_results.csv` had `confidence_factor` values corrupted to multi-comma
thousand-separator format (`"1,772,004,996"`) by an Excel-to-CSV round-trip. `clean_numeric()`
in `src/simulation_trans_rates_prep.r` only handled single-comma European decimal format and
silently set all confidence factors to NA → 0 → `slider_adjustment = 0` → `final_frac ≈ init_frac`
within machine precision → optimizer's `diffs == 0` constraint pinned area constant → all
off-diagonal transition rates collapsed to ~1e-11 (numerical noise) → Dinamica's Calc Change
Matrix rounded to zero cells.

## Open Items / Follow-up Concerns

### Concern 1 — Low allocation throughput (non-blocking for Phase 3.1)

The Remaining-Transitions matrix from Dinamica shows tens of thousands of unallocated cells per
from→to pair. Expander+Patcher only placed 4,477 actual transitions out of ~hundreds of
thousands requested by the change matrix. This points to **probability map saturation** or
**patch parameter restrictiveness** — Dinamica found enough high-probability eligible cells to
satisfy only a small fraction of the demand.

Candidates to investigate (outside Phase 3.1 scope):
- Probability map quality: are the predicted probabilities calibrated to historical transition
  frequencies, or systematically too low/concentrated?
- Patcher parameters (`Mean_Patch_Size`, `Patch_Size_Variance`, `Patch_Isometry` in `patcher_table.csv`)
- Expander `Perc_expander` values: many off-diagonal entries are very high (>90%) which may
  starve the Patcher of available cells

- **SC2**: TIF count verification — Phase 3.2's cross-stage audit script (SC5) will validate
