## Summary

The ALLOC-08 hard stop in Phase 3.3's operator gate is triggered because
`alloc_params.csv` on HPC contains no row for `id_trans=34`
(mining → high_intensity_agricultural, From\*=106, To\*=104), yet that id_trans
appears in each region's simulation trans_rates CSV. The root cause is a **stale
artifact problem, not a code bug**: the simulation trans_rates CSVs on HPC were
generated before Phase 3.2 Plans 01 and 02 were applied. Once re-generated with
the current code, two independent exclusion mechanisms will eliminate id_trans=34
before any CSV is written to disk.

The code in `src/simulation_trans_rates_prep.r` is **correct as committed**. No
source-level fix is required for Phase 3.4. The work is entirely a data re-run.

**Primary recommendation:** Pull the Phase 3.2 code to HPC, re-run
`submit_simulation_trans_rates_estimation.sh`, verify id_trans=34 is absent from
the regenerated CSVs, then re-run `submit_calibrate_allocation_parameters.sh`
before returning to the Phase 3.3 operator gate.

## Answer 1: Is the code in simulation_trans_rates_prep.r currently correct?

**Yes. The code is correct.** Both exclusion mechanisms are present and active in
the committed source.

### Mechanism A — Mining prohibition (config-driven class exclusion)

Located at `src/simulation_trans_rates_prep.r` lines 246–263 inside
`simulation_trans_rates_prep()`:

```r
forbidden_from_classes <- sim_config[["forbidden_from_classes"]]
if (is.null(forbidden_from_classes)) forbidden_from_classes <- character(0)
...
forbid_pairs_df <- if (length(forbidden_from_classes) > 0) {
  tidyr::expand_grid(
    region_name = NA_character_,
    From = forbidden_from_classes,
    To = setdiff(lulcs_global, forbidden_from_classes)
  ) %>%
    tibble::as_tibble()
} else {
  tibble::tibble(region_name = character(), From = character(), To = character())
}
```

Both `config/hpc_config.yaml` (line 101) and `config/local_config.yaml` (line 97)
have:

```yaml
forbidden_from_classes: ["mining"]
```

This expands to a row for every (mining → non-mining class) pair with
`region_name = NA`, meaning the rule applies globally across all regions. Because
the LULC class name for id_trans=34 is `mining → high_intensity_agricultural`, the
`From = "mining"` condition catches it here directly.

### Mechanism B — load_unmodelled_transitions (reconciliation-based exclusion)

Located at `src/simulation_trans_rates_prep.r` lines 22–46 and called at lines
265–274:

```r
unmodelled_df <- load_unmodelled_transitions(config)
message(sprintf(
  "  - Forbidding %d non-modelled (region, transition) pairs from reconciliation",
  nrow(unmodelled_df)
))
forbid_pairs_df <- dplyr::bind_rows(
  forbid_pairs_df,
  unmodelled_df
) %>%
  dplyr::distinct()
```

`load_unmodelled_transitions()` reads the reconciliation RDS from
`config[["transition_model_eval_dir"]]/<last_period>/transition_modelling_reconciliation_<period>.rds`
and extracts all rows where `model_status != "success"`, returning a data frame of
`(region_name, From, To)` pairs.

Since id_trans=34 has no trained model (calibration has no training data for
mining→high_intensity_agricultural), it will appear in the reconciliation RDS as a
non-success row. Mechanism B adds it to `forbid_pairs_df` with a per-region
`region_name` match, providing a second independent guard.

### How forbid_pairs_df is enforced downstream

`forbid_pairs_df` is passed through the call chain:

1. `simulation_trans_rates_prep()` → `run_scalar_optimization_loop()` (line 346)
2. `run_scalar_optimization_loop()` → `optimize_region_scenario()` (line 1461)
3. `optimize_region_scenario()` → `build_mats()` as `f_pair` (line 644)

Inside `build_mats()` (lines 442–449), `f_pair` is applied to `hard_forbid`:

```r
if (!is.null(f_pair) && nrow(f_pair) > 0) {
  fp <- f_pair %>% filter(region_name == reg | is.na(region_name))
  if (nrow(fp) > 0) {
    ii <- match(fp$From, cls)
    jj <- match(fp$To, cls)
    valid <- which(!is.na(ii) & !is.na(jj))
    hard_forbid[cbind(ii[valid], jj[valid])] <- TRUE
  }
}
```

Forbidden entries have both `rmin_mat[hard_forbid] <- 0` and `rmax_mat[hard_forbid] <- 0`
set, and `is_allowed[mats$hard_forbid] <- FALSE` forces the CVXR constraint
`multiply(x_t, Constant(1 - is_allowed)) == 0` (line 683). The optimizer is
structurally prevented from allocating any flow to mining→anything transitions.

### CSV output filter

After optimization, `optimize_region_scenario()` applies one more filter at lines
910–911:

```r
rate_df <- rate_df %>%
  dplyr::filter(!is.na(id_trans))
```

Persistence rows (From\* == To\*, which have no id_trans in the lookup) are
dropped here. But id_trans=34 would have already been zeroed out by the optimizer
constraints above, meaning if it somehow appeared in the output matrix, its Rate
would be 0 and it would not survive the `trans_rates_df` filter in `allocation.r`
(line 1704–1708, which drops Rate == 0 rows). There are three independent
defenses in depth.

**Conclusion:** The code correctly excludes id_trans=34. The stale CSVs on HPC
are the entire cause of ALLOC-08 firing.

No logic was changed. All three additions are purely observational.

### Critical implication

Because the stale HPC CSVs were generated before Plan 01's commit `9166fc4` (which
added the config-driven `forbidden_from_classes` and confirmed the YAML keys exist),
they were produced with the old hardcoded mining exclusion that **was already present
before Phase 3.2**. This means the stale CSVs may have already excluded mining
transitions via the hardcoded path — but the `load_unmodelled_transitions()` guard
may not have been executed, or the reconciliation RDS may not have existed at the
time the CSVs were last generated. The safest explanation is that the reconciliation
RDS was absent or had a different structure when the stale CSVs were run, causing
`load_unmodelled_transitions()` to `stop()` or the function itself not to exist
yet in the version that produced the stale CSVs.

In any case, re-running with current code on HPC will apply both mechanisms
correctly.

## Answer 4: Correct re-run sequence

The pipeline has two stale artifacts:

1. **Simulation trans_rates CSVs** — stale (produced before Phase 3.2 fixes)
2. **alloc_params.csv** — may or may not be stale, but must be regenerated after
   trans_rates CSVs are clean to guarantee coverage alignment

The correct sequence is:

```
Step 1: git pull on HPC (ensure allocation-step branch is current)
Step 2: sbatch scripts/submit_simulation_trans_rates_estimation.sh
        → regenerates all simulation trans_rates CSVs
        → AUDIT stage=4 lines confirm forbidden_excluded > 0 for each region
Step 3: Verify regenerated CSVs (see Answer 5)
Step 4: sbatch scripts/submit_calibrate_allocation_parameters.sh
        → regenerates alloc_params.csv from transition_feature_selection RDS
        → alloc_params will cover only modelled transitions
Step 5: Return to Phase 3.3 operator gate
        → sbatch submit_allocation job
        → ALLOC-08 stop should no longer fire
```

**Why alloc_params must be re-run even if it seems clean:**
`calibrate_allocation_parameters.r` reads from the `transition_feature_selection_summary`
RDS (lines 258–274), not from the simulation trans_rates CSVs. It therefore always
produces alloc_params covering only transitions with `selected_predictors` set
(i.e., successfully modelled transitions). However, if the existing alloc_params
was generated from a stale trans_rates CSV that included id_trans=34, there is no
guarantee the alloc_params has correct coverage. A clean re-run is the safe choice.

**Note on calibrate_allocation_parameters input source:**
The calibration does NOT read from the simulation trans_rates CSVs. It reads from
`config[["feature_selection_dir"]]/<period>/transition_feature_selection_summary_<period>.rds`
(lines 258–266). This RDS only contains transitions that survived feature selection,
which already excludes unmodelled transitions. This means alloc_params is
structurally sound once re-run — the stale trans_rates CSVs did not corrupt it.
The alloc_params re-run is precautionary to ensure version alignment.

## Common Pitfalls

### Pitfall 1: Re-running only trans_rates, not alloc_params
**What goes wrong:** Even with clean trans_rates CSVs, if alloc_params still has
stale rows, `allocation.r` line 1755's `setdiff()` check fires again.
**Prevention:** Always re-run both jobs in sequence.

### Pitfall 2: HPC git tree is stale
**What goes wrong:** `run_simulation_trans_rates_prep.r` sources the `src/`
directory relative to `$SLURM_SUBMIT_DIR`. If the HPC tree predates commit
`9166fc4`, the YAML key `forbidden_from_classes` is absent and the null-guard
in `simulation_trans_rates_prep.r` line 247 silently degrades to
`character(0)` — **the mining prohibition is silently disabled**, producing
CSVs that still include id_trans=34.
**Detection:** Check that the AUDIT stage=4 log shows `forbidden_excluded > 0`.
If it shows 0, the YAML key was not present.

### Pitfall 3: Scalar directory mismatch
**What goes wrong:** `allocation.r` reads CSVs from
`trans_rate_table_dir/simulation-lulc-areas-scalar-<selected_scalar>x/`.
If `config[["selected_scalar"]]` in `hpc_config.yaml` doesn't match a scalar
in `config[["simulation_trans_rates_params"]][["scale_factor"]]`, the CSV paths
won't exist and `allocation.r` line 700 returns NULL for every region.
**Prevention:** Confirm `selected_scalar` value is one of the scalars in
`scale_factor` list before submitting the allocation job.

### Pitfall 4: Reconciliation RDS absent on HPC
**What goes wrong:** `load_unmodelled_transitions()` calls `stop()` if the
reconciliation RDS is not found (lines 30–35). If the HPC has not run
`transition_modelling()` for the current period, the trans_rates job will fail
immediately.
**Prevention:** Verify the reconciliation RDS exists at
`config[["transition_model_eval_dir"]]/<last_period>/transition_modelling_reconciliation_<period>.rds`
before submitting the trans_rates job.

### Pitfall 5: Partial scalar output (job timeout)
**What goes wrong:** If the 4-hour wall time is insufficient for all scalar
iterations, only some scalars produce CSVs. The SLURM log will show the scalar
loop message for completed scalars only.
**Prevention:** Check that all expected scalar subdirectories
(`simulation-lulc-areas-scalar-Nx/`) exist after job completion. The job
summary at `trans_rate_table_dir/run_summary_<JOBID>.txt` records total runtime.
