# Summary — 03.5-03 Andes validation

## What was delivered

`03.5-VALIDATION.md` — the real-HPC validation of Phase 3.5 on the Andes, with a
before/after profile table vs the job-571309 baseline and the andes-eager control,
two-stage threading isolation, the numerical-equivalence result, the A3 verdict + bisect
fallback, and an honest residual-floor assessment.

## Outcome (PASSED)

- **Threading (Goal 2):** ~35× on the dominant predict (1→160 threads); `setup_inputs`
  2283 s vs the 20665 s baseline (~9×). Decisive win.
- **Lazy reads (Goal 1):** correct and equivalent; `predictor_preload` eliminated;
  resident floor ~20 GB lower on andes. Honest finding: the run *peak* (~206–216 GB) is
  driven by the single-shot predict transient on the 26M-cell from-class, not the
  predictor read, so peak is not reduced without `ALLOCATION_PREDICT_BATCH_ROWS`; the
  large floor win is Amazon-scaled (andes eager preload is only 24 GB vs ~80 GB Amazon).
- **Equivalence:** **bit-for-bit identical** (max|Δ| = 0.000e+00 over all 24 TIFs,
  NA-mismatch 0) between lazy+160 and eager+160; per-transition cell counts identical
  (no Pitfall-4 coverage loss).
- **A3:** settled favorably — lazy isolated read ~111 s vs eager 87.8 s, but end-to-end
  `setup_inputs` lazy 2283 s < eager 2389 s. `ALLOCATION_PREDICTOR_LAZY=0` bisect fallback
  proven (run 573776).
- **Bonus:** both runs completed the full pipeline incl. Dinamica (exit 0), beating the
  571309 baseline's unrelated dinamica_fail.

## Deviations from the plan

1. **Lazy read bug found & fixed mid-validation** (`fix(03.5-02)` d314504): the Arrow
   join key was int32 vs the parquet's int64 `cell_id`, so the lazy path failed at the
   first prediction (masked by furrr as `In index: 1`). The local testthat suite cannot
   catch this (arrow `SKIP`s without an install); the HPC smoke is the validation
   mechanism per REQUIREMENTS.md.
2. **Equivalence proven at matched 160 threads (bit-for-bit), not the planned 1-thread
   bit-for-bit + threaded <1e-6.** Running the two single-thread variants (~7 h each)
   was traded for one fast eager+160thr control; the result came back bit-for-bit (0.0),
   which is stronger than the planned <1e-6-at-threads, so the stricter 1-thread runs were
   unnecessary. `eager-1thr`/`lazy-1thr` configs remain in the driver if ever needed.
3. **Validation tooling added** (beyond the planned VALIDATION.md):
   `scripts/run_andes_validation.sh` (sequential, single-node, archiving driver with
   `VAL_RUNS`/`VAL_THREADS`/`VAL_BATCH_ROWS` knobs) and `scripts/compare_prob_maps.r`
   (cell-by-cell TIF equivalence). Required because three concurrent bare-`sbatch` smokes
   corrupted shared beegfs outputs and OOM'd a compute node.

## Follow-ups (not blocking this phase)

- mlr3 `predict_newdata()` is broken in `allocation_env` (`.__Task__col_info` missing) →
  always falls back to direct ranger prediction. Pre-existing env drift; worth a fix.
- Lazy per-from-class cache (`new.env`) does not evict; consider evicting a from-class
  after its transitions to keep the resident bound tight for the Amazon.
- Amazon run should use lazy + threading + `ALLOCATION_PREDICT_BATCH_ROWS` to realize the
  large memory-floor win and cap the predict transient.
