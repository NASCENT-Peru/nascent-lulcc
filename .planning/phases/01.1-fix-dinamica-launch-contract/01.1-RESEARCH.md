# Phase 1.1: Fix Dinamica Launch Contract — Research

**Researched:** 2026-05-15
**Domain:** Apptainer/Singularity container launch wiring, AppImage extraction, R subprocess shell-glue, HPC bash gate scripts
**Confidence:** HIGH on launch shape + container bootstrap (live HPC evidence + upstream Dockerfile verified verbatim); MEDIUM on the `.ego` binary-format question (decidable only by running on Euler)

## Summary

The seven Phase 1.1 failures (G1–G7) collapse to four shared root causes: (1) the Phase 1 `.def` bootstrapped from a non-existent GHCR image, so no operator could ever build a `.sif` from the committed definition; (2) `resolve_dinamica_launch()` was modelled on a documentation idiom (`apptainer exec <sif> DinamicaConsole`) that the upstream image's runtime contract does not actually expose — the AppImage's `bin/DinamicaEGO.sh` wrapper is the only entrypoint that sets the env vars Dinamica EGO 8 needs at runtime; (3) Apptainer 1.4's default bind-mount semantics hide the container's pre-seeded `$HOME/.dinamica_ego_8.conf` and `/tmp/dinamica` directories behind host bind mounts; and (4) `DinamicaConsole` returns exit 0 on `std::exception`, so the smoke test reports SUCCESS while Dinamica is dying. The remaining two findings (G5 smoke fixture wrong-format + G7 silent home fallback) are independent surface bugs that share no root cause with each other or with the other five.

All four root causes are addressable inside the file surface CONTEXT.md already names — the only new asset this phase introduces is a minimal smoke `.ego{-decoded}` fixture pair (DD-2 resolved below in favour of a sibling file, NOT replacement, because `src/dinamica_utils.r:512` already loads `allocation.ego-decoded` in production). DD-1 is resolved in favour of `rocker/r-ver:4.5.3` because the upstream Dockerfile already inlines geospatial install steps from its own `install_geospatial.sh` and bootstrapping from `rocker/geospatial:4.5.3` would duplicate work and triple the base layer pull (≈1.27 GB vs ≈348 MB).

**Primary recommendation:** Adopt the upstream `ethzplus/rocker-geospatial-dinamica` Dockerfile verbatim as the model for the rewritten `.def` `%post` (the verbatim content is reproduced below in Section 2). Hold the launch-shape change inside `resolve_dinamica_launch()` so no caller signature shifts. Defer the `.ego`-binary question to a single planning-time experiment that the planner schedules as Wave-1 Task 0.

### Pattern 1: Apptainer `--home` flag semantics
**What:** `--home <src>` (or `--home <src>:<dest>`) bind-mounts the host's `<src>` directory over the container's home location (default `/home/runner`) and sets `$HOME` inside the container to that path. Apptainer "automatically creates any missing bind points within the container using an overlay" `[VERIFIED: apptainer.org/docs/user/main/bind_paths_and_mounts.html]`.

**When to use:** Whenever the in-container application reads `$HOME/...` to find config files seeded at build time. Without `--home`, the host's `$HOME` is bind-mounted by default `[VERIFIED: same source — "system default bind points are $HOME, /sys, /proc, /tmp, /var/tmp, /etc/resolv.conf, /etc/passwd, $PWD"]`, which is exactly what hid `/root/.dinamica_ego_8.conf` in G3.

**Apptainer behaviour the planner must rely on:**
1. `--home /beegfs/dinamica-home` sets `$HOME=/beegfs/dinamica-home` inside the container AND binds the host directory there.
2. The host source directory MUST exist before launch; apptainer does NOT create it for you. **Task implication:** `resolve_dinamica_launch()` must `dir.create(staged_home, recursive = TRUE, showWarnings = FALSE)` before returning the command.
3. The `.dinamica_ego_8.conf` file MUST also exist (and have the right content) before launch. Task implication: write it on first run if missing, idempotent.
4. `--env KEY=VALUE` passes the env var to the contained process. Multiple `--env` flags can be repeated `[VERIFIED: apptainer.org/docs/user/1.4/cli/apptainer_exec.html]`.
5. `--cleanenv` strips host env before passing; do NOT use `--cleanenv` here — Dinamica relies on PATH/LD_LIBRARY_PATH exports set by the AppImage's `%environment` block.

**Example (verbatim shape D-104 mandates):**
```bash
# Source: synthesized from D-104, D-105, D-106 + apptainer 1.4 docs
apptainer exec \
    --home "$HPC_SCRATCH_ROOT/dinamica-home" \
    --env "DINAMICA_EGO_8_TEMP_DIR=$HPC_SCRATCH_ROOT/dinamica-tmp" \
    "$DINAMICA_EGO_8_HOME" \
    bash -c "cd /opt/dinamica/usr && bin/DinamicaEGO.sh /work/abs/model.ego"
```

### Pattern 2: Single-`bash -c` payload over multi-arg apptainer
**What:** Pass the full `cd + launcher + model` as a single `bash -c '...'` argument rather than as separate apptainer-level args.
**Why:** The `cd /opt/dinamica/usr` step is mandatory (G6 evidence: `bin/DinamicaEGO.sh` uses relative paths internally), but apptainer has no `--cwd` flag that runs before the command. Passing `bash -c '...'` keeps cd+launch atomic and side-steps any apptainer-quoting hazards with model paths containing spaces.
**Verified by:** Phase 1.1 CONTEXT.md `<specifics>` line 103 explicitly mandates this shape; live HPC test A `[CITED: 01-HUMAN-UAT.md G6]` proved `bash -c 'cd /opt/dinamica/usr && bin/DinamicaEGO.sh <abs-model.ego-decoded>'` produces a real Dinamica error vs. `std::exception` from direct invocation.

### Pattern 3: Post-hoc log grep for error-state detection
**What:** After `processx::run()` returns, the R code re-reads the log file from disk and greps for known error strings; if any match, raise an error regardless of subprocess exit code.
**When to use:** Any subprocess that exits 0 on internal errors (Dinamica is the example; `process_dinamica_script()` is an in-process R operation and does NOT need this).
**Source verified:** `src/dinamica_utils.r:313-321` already has a HALF-VERSION of this pattern (`grepl("Dinamica EGO exited with an error", res[["stdout"]])`); the work is to extend the grep set to all three strings AND read from the log file (not just `res$stdout`, which the tee path may not populate in some `processx` modes).

### Anti-Patterns to Avoid
- **Trusting `DinamicaConsole`'s exit code as the success signal.** Phase 1 already shipped this anti-pattern; it is the central cause of G2. The fix is post-hoc log grep, period.
- **Direct `apptainer exec <sif> DinamicaConsole <model>` without `bash -c 'cd …'` prelude.** Phase 1 shipped this too; G6 invalidates it. Even though the upstream Dockerfile's ENTRYPOINT runs DinamicaConsole directly, that path is for `docker run`, where the WORKDIR is set to `/model` and the env vars are seeded — neither holds for `apptainer exec` without explicit prelude.
- **Replacing `dinamica/dinamica_model/allocation.ego-decoded` instead of adding a sibling.** Production code in `src/dinamica_utils.r:512` `file.copy(decoded_file, …)` would silently start using the no-op smoke fixture as the allocation model. Always add a sibling under DD-2.
- **Hand-rolling apptainer bind-mount logic in shell or R.** Use `--home` and `--env` flags; do not bind `/tmp` or `/root` manually.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Apptainer bind-mount remapping | Custom `--bind /host:/container` chains for `$HOME` and `/tmp` | `--home <staged-home>` and `--env DINAMICA_EGO_8_TEMP_DIR=<staged-tmp>` | `--home` handles the `$HOME` env var AND the bind in one flag; `--env` is the canonical pass-through for env vars. ## Common Pitfalls

### Pitfall 1: Mismatched launch contract between R and shell smoke test
**What goes wrong:** `src/dinamica_utils.r:resolve_dinamica_launch()` and `scripts/smoke_test_dinamica.sh` drift apart over time; the smoke test stops mirroring the production launch.
**Why it happens:** Two implementations of the same contract in different languages.
**How to avoid:** **Single canonical comment block in both files**, plus a unit test that re-resolves the launch via `resolve_dinamica_launch()` and asserts the shell script's `LAUNCH_CMD` array matches the same args. The full shared-helper option (a `scripts/dinamica_launch_args.sh` that both source) is heavier than needed: R already has `processx`, and sourcing shell from R is fragile. **Recommended:** Comment + assertion test. See Section 7 below for the decision.
**Warning signs:** Smoke test exits 0 but real allocation fails; or smoke test fails but real allocation works.

### Pitfall 2: Forgetting absolute model path
**What goes wrong:** D-106 says model path MUST be absolute; the AppImage launcher's relative-path branch is fragile under `cd /opt/dinamica/usr`.
**Why it happens:** `processx::run()` doesn't auto-normalize paths; the developer might pass `model.ego` thinking the `cd` doesn't affect arg resolution. It does — the `bash -c` payload runs after `cd`, and the launcher resolves the model path relative to the new cwd.
**How to avoid:** `resolve_dinamica_launch()` calls `normalizePath(model_path, mustWork = FALSE)` before splicing into the bash payload. Add a test that passes a relative `model_path` and asserts the resolved args contain an absolute path.
**Warning signs:** `bin/DinamicaEGO.sh: cannot find /opt/dinamica/usr/model.ego` in the log.

### Pitfall 3: `.dinamica_ego_8.conf` seeding race
**What goes wrong:** Two parallel allocation workers both try to create `<staged-home>/.dinamica_ego_8.conf` simultaneously; one wins, the other reads partial content.
**Why it happens:** `resolve_dinamica_launch()` creates the staged-home lazily on first call. Multiple workers may hit it on the first run.
**How to avoid:** Write to a tempfile and `file.rename()` atomically; OR seed the staged-home and conf file in a Wave-1 pre-flight task that runs BEFORE workers spawn (recommended — keeps the launch helper pure). The pre-flight idiom is already established by `validate_allocation_runtime()`.
**Warning signs:** Rare flaky `Dinamica EGO startup error: cannot read .dinamica_ego_8.conf` in the log on early runs.

### Pitfall 4: HPC detection succeeds but `HPC_SCRATCH_ROOT` is unset and the operator is NOT on Euler
**What goes wrong:** A developer SSHs into a non-Euler Linux host that happens to have `/beegfs` mounted (rare but possible at ETH). D-112 detection fires, but they don't have `HPC_SCRATCH_ROOT` exported. Script exits.
**Why it happens:** Detection is OR-of-three signals; `/beegfs` is the false-positive vector.
**How to avoid:** The error message MUST tell them which signal fired and how to override (e.g., `export HPC_SCRATCH_ROOT=<path>` OR `unset SLURM_JOB_ID` OR run with `--no-hpc-detect`). Don't add a `--no-hpc-detect` flag unless asked — first version: clear message that names which signal fired.
**Warning signs:** Operator complains the script "broke for no reason" on a non-Euler Linux host.

### Pitfall 5: Smoke `.ego` produced by `process_dinamica_script()` may not actually be a valid `.ego` binary
**What goes wrong:** `process_dinamica_script(mode="encode")` is a TEXT-TO-TEXT transformation that base64-encodes `Calculate(R|Python)Expression` blocks but otherwise renames `.ego-decoded` content to `.ego`. DinamicaConsole MAY accept this format or MAY only accept the proprietary binary `.ego` saved by Dinamica EGO GUI's "Save Model" action. **The G5 finding** (`The ".ego-decoded" does not represent a supported model script format`) is an extension-based rejection (file's `.ego-decoded` extension fails the check), not a content-based one — strongly suggesting that the same content with `.ego` extension is accepted. But this has not been verified end-to-end against the rebuilt `.sif` on Euler. Production allocation reportedly works through this path; if Phase 1 production never actually ran on Euler against the rebuilt image, this is unverified.
**How to avoid:** Wave-1 plans the experiment: build a minimal `.ego-decoded` with no R/Python chunks, run `process_dinamica_script(infile, outfile)` to produce a `.ego`, run the live smoke test once, observe result. If accepted: commit both. If rejected: fall back to GUI-built `.ego` per D-110.
**Warning signs:** `[live] FAIL ... terminate called after throwing` or `unsupported model script format` against the new smoke fixture.

## Decision Resolutions (eight research targets)

### Target 1: Can `process_dinamica_script(mode="encode")` produce a binary `.ego` from a minimal `.ego-decoded`? (decides D-110, DD-2)

**Finding:** `process_dinamica_script()` is a TEXT-to-TEXT transformation. It reads the input as text (`readChar(infile, file.info(infile)$size)`), base64-encodes any `CalculateRExpression` / `CalculatePythonExpression` chunks it finds, and `writeChar()`s the result. The output extension is whatever the caller passes in `outfile`. It does NOT produce a compiled-binary `.ego` artifact distinct from the `.ego-decoded` text format — the production allocation path works (per Phase 1 verification report) by writing the encoded text to a `.ego`-extension file, and DinamicaConsole accepts that.

**Key signal:** The G5 error message `The ".ego-decoded" does not represent a supported model script format` is an **extension-based** rejection (DinamicaConsole rejects `.ego-decoded` files by extension), not a content-based one. The same content under `.ego` extension is the path the production allocation has always followed.

**Edge case:** The function's check at line 363 stops on empty `matches`: `any(!non_base64_chars_present)` on `logical(0)` returns `FALSE`, so a minimal `.ego-decoded` with **no R/Python chunks at all** passes the check vacuously and produces a literal-copy output. Confirmed by R semantics: `any(!logical(0))` → `FALSE`.

**Decision support for D-110:** A no-op minimal `.ego-decoded` (just `@charset`, `@date`, `@version`, and a trivial `Script {{ }}` body) SHOULD round-trip through `process_dinamica_script()` and be accepted by DinamicaConsole. **Confidence: MEDIUM** — high on the function semantics, but the actual DinamicaConsole acceptance of a no-op script is decidable only by running on Euler.

**Decision support for DD-2:** Production code at `src/dinamica_utils.r:512` does `decoded_file <- file.path(model_dir, "allocation.ego-decoded")` and `file.copy(decoded_file, …)`. **Replacing `allocation.ego-decoded` would BREAK production.** **DD-2 must add a sibling.** Recommend `dinamica/dinamica_model/smoketest.ego-decoded` + `dinamica/dinamica_model/smoketest.ego`.

**Planner action:** Wave-1 Task 0 (gating): write the minimal `.ego-decoded`, run `process_dinamica_script()` locally to produce `.ego`, then run the live smoke test against the new `.sif` on Euler. If it passes, commit both files and proceed. If DinamicaConsole rejects the no-op `.ego`, fall back to GUI-built `.ego` and commit as binary asset.

### Target 7: Launch contract drift risk between R-side and shell-side (CONTEXT.md `<code_context>` flag)
