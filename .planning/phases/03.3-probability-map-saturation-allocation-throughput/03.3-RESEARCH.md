## Summary

Phase 3.3 ships a single-source structural writer inside `src/allocation.r` that materialises all four Dinamica inputs — work_dir `trans_rates.csv`, `expansion_table.csv`, `patcher_table.csv`, and `probability_map_dir/*.tif` — from one filtered, id_trans-sorted data frame so that **row position N in the rate table equals alphabetic position N in the probability-map cube by construction**. The empirical root cause from Phase 3.1 (~1% allocation throughput on BAU × costa_peruana × 2022→2026) was a misalignment: the TIF writer at `src/allocation.r:2265-2316` iterates with `k = seq_len(.N)` but skips rows where `from_val == to_val || rate == 0`, producing prefix gaps (001, 002, 003, _, 005, ...) while `expansion_table.csv` and `patcher_table.csv` retain all original rows. Dinamica's `CreateCubeOfProbabilityMaps` submodel calls `ListFilenames` (which `sorted()`s the directory) and binds cube layer s to row s of the transition matrix via `ExpandTableToUniqueKeys` (which assigns UniqueIndex 1..N in input row order). Result: the wrong probability map is consulted for each transition, so Expander+Patcher get garbage signal and only the one accidentally-aligned transition (103→105) placed cells.

The fix is mechanical: filter the work_dir rate CSV to drop persistence (`from == to`) and zero-rate rows BEFORE any of the four artifacts are written, sort by `id_trans` ascending, and write all four artifacts from the same data frame in lockstep. The Stage 4 source rate CSV on disk is unchanged (Phase 3.2's cross-stage audit still consumes the full row set). The existing alloc_params warning at `src/allocation.r:1707` is promoted to a hard `stop()` so any missing calibration entry surfaces immediately rather than producing silently-truncated expansion/patcher tables.

Inline saturation metrics are emitted at the end of each region run as `saturation_summary.csv` in work_dir plus a structured `AUDIT stage=saturation ...` log line (mirroring the Phase 3.2 AUDIT prefix convention which Phase 3.2 will introduce in `transition_modelling.r`, `simulation_trans_rates_prep.r`, and `allocation.r`). A standalone `scripts/diagnose_allocation_saturation.r` reads the same artifacts plus the Dinamica log's Remaining-Transitions matrix and `posterior.tif` for a deeper post-hoc diff against demanded cells. Both surfaces call the same R helpers (factored into `src/allocation.r` or a new `src/saturation_diagnostics.r`).

The per-transition floor is config-driven: `simulation_trans_rates_params.saturation_threshold` (default 0.90) and `simulation_trans_rates_params.saturation_exempt` (initially empty list of `{from_lulc, to_lulc, reason}` records). Verification runs BAU × all 4 Peruvian regions × first simulation timestep (2022→2026). Spatial autocorrelation, Patcher tuning, Expander rebalancing, and probability post-processing are explicitly deferred per CONTEXT.md D-07/D-10.

**Primary recommendation:** Refactor `prepare_region_worker_inputs()` and `generate_probability_maps()` into a single-source writer keyed by `id_trans`. Drop persistence/zero-rate rows once at entry. Promote the alloc_params warning to `stop()`. Ship inline + standalone saturation diagnostics that share helper functions. Do NOT add a runtime alignment assertion — the writer makes misalignment unreachable by construction.

### Dinamica Alignment Contract — Exact Mechanics

`dinamica/dinamica_model/evoland_ego_Submodels/ListFilenames.ego-decoded:51` runs `files = sorted(files)` (Python lexicographic sort of the absolute paths). So if `probability_map_dir/` contains `001_id_trans_1.tif, 002_id_trans_2.tif, ..., NNN_id_trans_X.tif`, the sorted list places file index 1 at position 1 in the `getFileNames` table (which is what `getTableValue92360 { keys = layer }` looks up).

`dinamica/dinamica_model/evoland_ego_Submodels/ExpandTableToUniqueKeys.ego-decoded:25-30` builds the iteration as:
```python
uniqueIndex = 1
for rowIndex in range(1, len(dinamica.inputs["t1"])):
  row = dinamica.inputs["t1"][rowIndex]
  row.insert(0, uniqueIndex)
  newTable.append(row)
  uniqueIndex += 1
```
This assigns `UniqueIndex` 1..N **in input row order**. The transition matrix is `trans_rates.csv` from work_dir. So for each row s in `trans_rates.csv`, Dinamica looks up the s-th file from `ListFilenames` (alphabetic). **Row order in `trans_rates.csv` MUST equal alphabetic order of probability TIFs.** Three-digit zero-padded prefixes (`%03d`) survive lex sort up to 999 rows, which is comfortably above the ~30-row regime.

[VERIFIED: `dinamica/dinamica_model/evoland_ego_Submodels/CreateCubeOfProbabilityMaps.ego-decoded:3-15, 21-25, 116-138`; `ListFilenames.ego-decoded:51`; `ExpandTableToUniqueKeys.ego-decoded:25-30`]

### Pattern 4: Inline saturation summary

**What:** At end of `run_allocation_one_timestep()` (after Dinamica returns), call helpers in `src/saturation_diagnostics.r` to compute per-transition `placed_cells` (diff anterior vs posterior), `demanded_cells` (`Rate × area_t`), coverage, percentiles, demand-vs-capacity, and write `saturation_summary.csv` + `AUDIT stage=saturation ...` line.

**Example:**
```r
# Source: new src/saturation_diagnostics.r
compute_per_transition_metrics <- function(
  filtered_df, alloc_params, prob_map_dir,
  anterior_path, posterior_path, log_file, threshold, exempt
) {
  anterior <- terra::rast(anterior_path)
  posterior <- terra::rast(posterior_path)
  anterior_vals <- terra::values(anterior, mat = FALSE)
  posterior_vals <- terra::values(posterior, mat = FALSE)

  # Total valid (non-NA) cells of the FROM class — area_t denominator
  metrics <- lapply(seq_len(nrow(filtered_df)), function(k) {
    from_val <- filtered_df[["From*"]][k]
    to_val   <- filtered_df[["To*"]][k]
    rate     <- filtered_df[["Rate"]][k]
    id_t     <- filtered_df[["id_trans"]][k]

    area_t <- sum(anterior_vals == from_val, na.rm = TRUE)
    demanded_cells <- round(rate * area_t)
    placed_cells   <- sum(
      anterior_vals == from_val & posterior_vals == to_val,
      na.rm = TRUE
    )
    placed_frac <- if (demanded_cells > 0L) placed_cells / demanded_cells else NA_real_

    # Load this transition's probability map; compute coverage + percentiles
    tif_path <- file.path(prob_map_dir, sprintf("%03d_id_trans_%d.tif", k, id_t))
    prob_rast <- terra::rast(tif_path)
    prob_vals <- terra::values(prob_rast, mat = FALSE)
    prob_vals <- prob_vals[!is.na(prob_vals)]
    n_valid <- length(prob_vals)
    coverage <- if (n_valid > 0L) sum(prob_vals > 0) / n_valid else NA_real_

    quants <- if (n_valid > 0L) {
      stats::quantile(prob_vals, c(0.5, 0.9, 0.95, 0.99, 1.0), na.rm = TRUE)
    } else {
      rep(NA_real_, 5)
    }
    cells_above_p50 <- if (n_valid > 0L) sum(prob_vals >= quants[[1]], na.rm = TRUE) else 0L
    demand_vs_capacity <- if (cells_above_p50 > 0L) demanded_cells / cells_above_p50 else NA_real_

    is_exempt <- any(
      vapply(exempt, function(e) e$from_lulc == from_val && e$to_lulc == to_val, logical(1))
    )
    floor_met <- !is.na(placed_frac) && placed_frac >= threshold

    data.frame(
      id_trans = id_t, from_val = from_val, to_val = to_val,
      rate = rate, demanded_cells = demanded_cells, placed_cells = placed_cells,
      placed_frac = placed_frac, coverage = coverage,
      p50 = quants[[1]], p90 = quants[[2]], p95 = quants[[3]],
      p99 = quants[[4]], pmax = quants[[5]],
      demand_vs_capacity = demand_vs_capacity,
      exempt = is_exempt, floor_met = floor_met
    )
  })
  do.call(rbind, metrics)
}
```

### Anti-Patterns to Avoid

- **Adding a runtime alignment assertion AFTER the writers ran.** Wrong layer of defence. D-02 makes alignment unreachable by construction; an assertion would only catch a bug in the writer itself, which a unit test catches better. Adding both is belt-and-suspenders for the wrong reason.
- **Sorting by `(From*, To*)` lexicographically.** Phase 3.2 RESEARCH (and Phase 3.1 fixes) standardized on `id_trans` as the cross-stage stable key. Lexicographic sort on `(From*, To*)` would reorder differently and break the join semantics that Phase 3.2 just hardened.
- **Filtering the Stage 4 source CSV on disk.** Out of scope and would break Phase 3.2's cross-stage audit (`scripts/audit_transition_pipeline.r` reads the Stage 4 source). D-03 explicitly scopes the filter to the work_dir copy only.
- **Computing spatial autocorrelation as part of the saturation summary.** Explicitly deferred by D-07.
- **Implementing Patcher/Expander tuning preemptively.** D-10 — ship alignment fix and re-measure first.

## Common Pitfalls

### Pitfall 1: Stage 4 source CSV vs work_dir copy semantics drift

**What goes wrong:** Phase 3.2's cross-stage audit (`scripts/audit_transition_pipeline.r`, in flight) reads the Stage 4 source rate CSV directly to count rows per (scenario, region, timestep). If Phase 3.3 accidentally applies the persistence+zero-rate filter to the source CSV, Phase 3.2's audit suddenly sees fewer rows and reports a false discrepancy with Stage 1's viable_transitions_lists.csv.

**Why it happens:** It's tempting to filter once at Stage 4. CONTEXT.md D-03 explicitly forbids this.

**How to avoid:** Apply the filter in memory on the in-Stage 5 copy ONLY. The work_dir `trans_rates.csv` becomes the filtered artifact; the Stage 4 source CSV on disk is read-only from Stage 5's perspective.

**Warning signs:** Phase 3.2 audit reports rate_csv_rows ≠ viable_input − forbidden_excluded for a scenario × region where Phase 3.3's filter would have applied.

### Pitfall 2: Generating empty placeholder TIFs at "missing prediction" rows

**What goes wrong:** Even with persistence/zero-rate dropped, an active id_trans might somehow have no probability predictions (e.g. an mlr3 model loaded but produced all-NA outputs for the from-class cells in this region). The current code at `src/allocation.r:2275-2278` does `next` on `nrow(dt_j) == 0L`, which produces a gap in the `%03d` sequence and breaks alignment.

**Why it happens:** mlr3 prediction failures, region masking removing all from-class cells, race conditions on cached predictions.

**How to avoid:** When `nrow(dt_j) == 0L`, write an all-NA TIF with the correct `%03d` prefix anyway so the alphabetic sequence stays gap-free. Log a WARN. (Dinamica reading the cube will see an all-NA layer, which Expander+Patcher handles as a zero-probability layer — no allocation for that transition, but no misalignment downstream.)

**Warning signs:** Region log shows "WARN id_trans=X row=Y has no predictions; wrote empty TIF" — investigate whether the model file is valid and whether the from-class has cells in the region.

### Pitfall 3: `Rate × area_t` denominator unit mismatch

**What goes wrong:** Computing demanded_cells as `Rate × total_valid_cells_in_region` instead of `Rate × cells_in_from_class`. Stage 4's `Rate` is in fraction-of-from-class space (see `src/simulation_trans_rates_prep.r:857-860`: `rate_mat <- x_val / pmax(area_t / scale_fac, 1e-12)` — flow over from-class area). So `demanded_cells = Rate × |cells where lulc == from_val|`, NOT `Rate × |valid cells in region|`.

**Why it happens:** The unit confusion that bit Phase 3.1 (commit `703174b`); easy to repeat in the diagnostic.

**How to avoid:** Always use `sum(anterior_vals == from_val, na.rm = TRUE)` as the multiplier. Document this in the helper function docstring. Add a unit test against a tiny synthetic raster where the expected `demanded_cells` is hand-computable.

**Warning signs:** Demand-vs-capacity ratios that look implausibly large (>> 1.0 for transitions with high probability coverage) or `demanded_cells > area_t`.

### Pitfall 4: Aliases / column-name marker characters in CSV round-trips

**What goes wrong:** Dinamica requires `From*` and `To*` column markers (asterisk indicates key column). `read.csv(check.names = TRUE)` (the default) mangles these into `From.` and `To.`. The current code at `src/allocation.r:1674` correctly uses `check.names = FALSE`, but any new helper that re-reads CSVs must do the same. Also: commit `2c599a2` ("Fix Dinamica table column format: preserve From*/To* key markers and drop id_trans") shows the alloc_params table needs id_trans dropped before being passed to Dinamica.

**Why it happens:** R defaults; copy-paste from a different read.csv call site.

**How to avoid:** All `read.csv()` calls in new code use `check.names = FALSE`. All `write.csv()` calls of Dinamica-bound artifacts strip `id_trans` (the column is for our R-side joining only; Dinamica's `expansion_table.csv` and `patcher_table.csv` should be `From*`, `To*`, plus the param columns — same as the current writer at lines 1719-1762). For the work_dir `trans_rates.csv`, retain `id_trans` because Dinamica simply ignores extra columns.

**Warning signs:** Dinamica log emits `Cannot find column "From*"` or returns `std::exception`. Phase 1.1's three-pattern grep at `src/dinamica_utils.r:.check_dinamica_post_run()` catches these.

### Pitfall 5: alloc_params row order vs trans_rates row order

**What goes wrong:** After dropping the persistence/zero-rate rows from `trans_rates_df`, the existing code at `src/allocation.r:1698-1700` subsets `alloc_params` by `id_trans %in% trans_rates_df$id_trans` but does not re-order to match `trans_rates_df`. Dinamica's `expansion_table.csv` and `patcher_table.csv` are PercentMatrix / TransitionFunctionParameterMatrix types — they key on `From*/To*` (per `AllocateTransitions.ego-decoded:24-26, 41-54`) so row order arguably doesn't matter for them, BUT keeping them in the same id_trans-ascending order as the cube is a defence-in-depth measure if a future Dinamica version changes lookup semantics.

**How to avoid:** Use `alloc_params[match(trans_rates_df$id_trans, alloc_params$id_trans), ]` to enforce identical row order across all three CSVs.

**Warning signs:** None at runtime (Dinamica uses keyed lookup for these tables) but unit tests should still assert identical row order across all three CSVs.

### Pitfall 6: `selva_andina` is a TRAINING-region label, not a runtime region

**What goes wrong:** CONTEXT.md mentions `selva_andina` appearing in `scripts/test_qs_roundtrip.r:11` (`water_body-mining_selva_andina.qs`). One might assume Peru has a 5th region called "selva_andina". Reading `src/region_prep.r:9-37` shows region labels come from `regions.shp` column `Workshop_r` (lowercased, spaces→underscores). The transition_modelling output files are named `{from_class}-{to_class}_{region_label}.qs`. `selva_andina` IS a region label — it just happens to NOT be `costa_peruana` (the one Phase 3.1 smoke tested).

**How to avoid:** Read `regions.json` at runtime to enumerate the actual list. Don't infer from filenames. See Question 2 resolution below.

**Warning signs:** Hardcoding "costa_peruana, sierra_peruana, selva_peruana" anywhere — always derive from `regions.json`.

### Q1 — Dinamica iteration semantics (HIGH confidence, verified by reading ego-decoded files)

**Question:** When `ExpandTableToUniqueKeys` iterates the transition matrix and `getTableValue92360` looks up the s-th file by `keys = layer = s`, does Dinamica use the row index of the rate table as written, or does it re-sort by (From*, To*) lexicographically?

**Answer:** **Row index of the rate table AS WRITTEN — no re-sort.** `ExpandTableToUniqueKeys.ego-decoded:25-30` shows a plain Python `for rowIndex in range(1, len(table))` loop that assigns `uniqueIndex` 1..N in input order. **Implication:** The single-source writer keying on `id_trans` ascending is correct. No additional `(From*, To*)` sort is needed; in fact adding one would risk breaking the id_trans → row position invariant if any pathological numeric-vs-character sort behaviour kicked in.

### Q6 — Demand denominator semantics (HIGH confidence, verified by reading simulation_trans_rates_prep.r)

**Question:** What is the computational identity linking Dinamica's "Remaining Transitions" matrix back to `(Rate × area_t)`? Where exactly does the diagnostic's "demanded" number come from?

**Answer:** From `src/simulation_trans_rates_prep.r:855-860` and the conventions Dinamica's `CalcChangeMatrix` enforces:
- Stage 4 writes `Rate` such that `Rate[i,j] = flow[i,j] / area[i]_in_fraction_space` where `flow` and `area` are the optimizer's outputs and both share `scale_fac` scaling.
- At allocation time, Dinamica's `CalcChangeMatrix landscape transitionMatrix` (`AllocateTransitions.ego-decoded:77`) computes the demanded number of cells per (from, to) pair as roughly `Rate[i,j] × |cells where landscape == i|` — i.e. multiplies the rate by the present count of from-class cells.
- So the diagnostic's **demanded denominator** for transition (i, j) is:
  ```
  demanded_cells = Rate[i,j] × count(anterior_vals == i)
  ```
  where `count(anterior_vals == i)` is computed once per from-class.

[VERIFIED: `src/simulation_trans_rates_prep.r:855-860`; `dinamica/dinamica_model/evoland_ego_Submodels/AllocateTransitions.ego-decoded:77`]

**Dinamica's "Remaining Transitions" matrix** (as observed in `03.1-UAT.md` lines 53-62) reports `demanded − placed` per (from, to) cell after Expander + Patcher run. So:
```
demanded_from_dinamica_log[i,j] = remaining_transitions[i,j] + placed[i,j]
```
The diagnostic can either:
(a) **Re-derive demanded from Rate × area_t** (the inline approach — fast, no log parse needed), or
(b) **Parse the Dinamica log for the Remaining-Transitions matrix and add to placed** (the standalone approach for cross-validation).

The standalone diagnostic uses both methods and reports any drift between them as a sanity check.
