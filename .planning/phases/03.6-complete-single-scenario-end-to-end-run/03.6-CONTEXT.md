# Phase 03.6: Complete Single-Scenario End-to-End Run - Context

**Gathered:** 2026-06-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Drive a single scenario (BAU) to completion across **all regions × all timesteps**,
producing posterior rasters for every region/timestep plus national mosaics — the capstone
proof that the Phase 3 machinery works at scale (validated lazy per-from-class reads + scoped
threaded prediction from 3.5, corrected transition pipeline from 3.2, probability-map
saturation + int32-cube Dinamica allocation from 3.3/3.4).

This is the unmet portion of the Phase 3 parent goal. **Single scenario only.** Explicitly
NOT in scope (these belong to Phase 4): the multi-scenario sweep / Rundeck node-packing (S2),
full transition-level atomic resumability (Phase 4 SC3), block-wise predict performance
(PERF-01), terra/CVXR/intervention-path correctness ports, and per-region saturation *tuning*.

The capstone so far — the "andes full run" cited for 3.3/3.4/3.5 — was **one region × one
timestep** (BAU × andes × 2022→2026, scoped via `ALLOCATION_YEAR_POST_FILTER`). The full
multi-timestep chain and multi-region orchestration have never been exercised end-to-end.
That is the work of this phase.

</domain>

<decisions>
## Implementation Decisions

### Run Topology & Node Sizing

- **D-01:** **Per-region parallel jobs.** Launch one SLURM job per region via the existing
  `ALLOCATION_REGION_FILTER` knob (`src/allocation.r:454` `filter_allocation_regions()`); each
  job runs that region's full serial timestep chain. Wall time ≈ the heaviest region's chain
  (andes), not the sum across regions. Timesteps stay serial within a region (each posterior
  chains into the next anterior); regions run concurrently.

- **D-02:** **One highmem/fat ~256 GB node per region, one region per node.** andes peaked
  ~129 GB private RSS for a *single* timestep post-3.5 (`andes-lazy-threads-573721.out`:
  `peak_rss=129481.2MB`), so ~256 GB gives headroom. Jobs MUST request
  `--partition=highmem`/`fat` (or equivalent `--mem`) — bare `sbatch` defaults to the
  ~93 GB compute partition and OOMs. Planner derives `--mem`/flavor per region from actual
  `peak_rss` profiles (andes known; others TBD on HPC). No region-packing in this phase.

- **D-03:** **National mosaic assembled post-hoc for every timestep.** After all per-region
  jobs finish, a mosaic-assembly step stitches the per-region posteriors into a national
  `posterior_<year>.tif` for **every** timestep (matches the `posterior_2026.tif` naming the
  current driver already emits at `src/allocation.r:1804`). The combined national time series
  is part of the deliverable.

- **D-04:** **Thin launcher script is the capstone artifact.** Add a small wrapper (e.g.
  `scripts/submit_allocation_scenario.sh`) that fans out one job per region (SLURM array or
  loop) with `ALLOCATION_REGION_FILTER` + per-region `--mem`/`--partition` set, then queues a
  **dependent** mosaic-assembly job (`afterok`) that produces the national mosaics. Reproducible
  and documented — not a hand-typed `sbatch` recipe living only in operator memory. Model it on
  the existing `scripts/submit_allocation*.sh` family.

- **D-05:** **Decouple per-region chaining from the shared mosaic write (required for D-01).**
  The current driver's per-timestep mosaic writes to a *region-agnostic* path
  (`scenario/<year>/posterior_<year>.tif`, `src/allocation.r:1804`) and returns *that mosaic*
  as the next timestep's anterior (`run_allocation_one_timestep` return →
  `run_allocation_for_scenario` loop, `src/allocation.r:1514-1543`). Under per-region parallel
  jobs this **collides**: concurrent regions clobber the same `posterior_<year>.tif`, and each
  per-region chain would wrongly chain on a single-region-extended mosaic. Fix: each per-region
  chain must chain on its **own** region posterior (the region work_dir posterior, namespaced so
  there is no shared-path collision), and the national mosaic is produced ONLY by the post-hoc
  assembly job (D-03). The planner must verify each per-region chain reads back its own prior
  posterior as its anterior slice (region footprints are disjoint, so a region only needs its own
  cells).

### Completion / Acceptance Bar

- **D-06:** **Blocking bar = existence + differs-from-anterior + all regions.** "Complete"
  means: for **every** region × **every** timestep there is a valid GeoTIFF posterior that
  **differs from its anterior** (rules out the degenerate "nothing happened" case), the national
  mosaic exists for every timestep (D-03), and **all** regions finished all timesteps
  (D-09). A persistently-failing region is a blocker tracked to resolution or escalated to
  Phase 4 — not silently dropped.

- **D-07:** **Saturation is logged, NOT blocking.** The per-timestep saturation surface from
  3.3 (`saturation_summary.csv` + `AUDIT stage=saturation ...`, 3.3 D-05/D-08) is computed and
  recorded for every region × timestep, but does NOT gate completion. andes' first timestep
  already logged `met=22 exempt=0 failed=2`; gating the capstone on ≥90%/transition every step
  would turn 3.6 into a saturation-tuning phase (which is deferred). Saturation is reported
  alongside completion as a quality signal, aggregated into the manifest (D-08).

- **D-08:** **A run-manifest / checker script declares completion (the durable capstone
  evidence).** It inventories `posterior.tif` across the full region × timestep matrix, confirms
  `count == regions × timesteps`, confirms the national mosaics exist, aggregates saturation and
  the plausibility QA (D-08b), and emits **PASS / INCOMPLETE**. This artifact is the proof
  Phase 3.6 is done — not log eyeballing.

- **D-08b:** **Lightweight automated trajectory plausibility QA.** A small checker aggregates
  per-timestep, per-region LULC class areas across the chain and flags implausible jumps,
  demand mismatches, or degenerate (e.g. all-one-class) maps. A single posterior *existing* does
  not prove a ~9–10-step serial chain stayed sane to 2058/2060; this is cheap insurance against
  silent drift. Flags surface in the manifest (D-08) as quality signals; hard degeneracy
  (all-one-class) escalates to INCOMPLETE, soft demand-mismatch is a warning.

### Failure / Resume Policy

- **D-09:** **Timestep-level resume (coarse).** On restart of a dead per-region job, the launcher
  detects the last completed timestep for that region (posterior for `<year>` exists) and
  resumes the chain from the **next** timestep, reusing the existing
  `ALLOCATION_YEAR_POST_FILTER` / start-year override and the prior posterior as anterior. Granularity
  is region × timestep — NOT transition-level. Avoids re-running hours of completed timesteps;
  reuses existing knobs. Full transition-level atomic resumability stays Phase 4 (SC3).

- **D-10:** **Atomic posterior writes (`.tmp.tif` → rename).** Per-timestep posterior + mosaic
  writes go to a `.tmp` path then `file.rename` into place, so a job killed mid-write can't leave
  a half-written posterior that the D-09 resume mistakes for complete. This is the small,
  high-value slice of Phase 4 SC3 pulled forward; the rest of atomic/transition-level
  resumability remains Phase 4.

### Timestep Schedule (flagged default — confirm during research)

- **D-11:** **Reconcile the schedule to ONE authoritative source before the run; the run can
  only use the schedule that has matching rate tables.** There is live drift: the driver builds
  steps from a uniform `step_length: 4` (`src/allocation.r:1480` →
  `seq(2022, 2056, 4)` → ends 2058, 9 steps, never reaches 2060), while config declares an
  explicit irregular `simulation_year_steps: [2022, 2024, 2028, …, 2060]` (10 boundaries,
  per [03.2 D-01]). The live andes run followed `step_length=4` (produced 2026, not the list's
  2024). **Default recommendation:** treat `simulation_year_steps` as authoritative (per 03.2
  D-01) and reconcile the loop to it. **BUT the planner MUST first verify on HPC which schedule
  the existing per-`year_ant` `trans_rates` CSVs and demand tables
  (`tools/simulation_lulc_areas_2060.csv`) were generated for** — the run can only use the
  schedule with matching rate tables. If rate CSVs exist only for 2022 (single-timestep so far),
  every later `year_ant` needs its CSV → likely a Stage-4 re-run prerequisite, echoing Phase 3.4.
  This is a hard prerequisite, not a nicety.

### Claude's Discretion

- Exact region list/labels and count (3 vs 4; andes / amazon / costa / selva_andina naming) —
  resolve from `inputs/regionalization/regions.json` on HPC (`config[["reg_dir"]]`); empty in the
  repo checkout, authoritative on scratch.
- SLURM array vs loop for the fan-out; exact `--mem`/partition values per region (from profiles).
- Whether the manifest/plausibility checker is one script or two; output format (CSV + log line
  vs report); reuse of the 3.3 `saturation_diagnostics.r` / `verify_phase3_smoke.sh` helpers.
- Concurrency policy for the per-region jobs (submit all at once vs staggered) given queue limits.

</decisions>

<specifics>
## Specific Ideas

- The full run is large: andes alone = ~1.25 h and ~129 GB peak for **one** timestep. With
  ~9–10 timesteps per region, a single integrated job would be tens of hours and a single OOM
  would kill everything — hence the per-region parallel decomposition (D-01) and atomic-write +
  resume safety (D-09/D-10).
- "differs-from-anterior" (D-06) is deliberately the floor, not saturation quality — the user
  framed 3.6 as proving the *machinery runs to completion at scale*, with saturation/tuning as a
  separate concern (consistent with 3.3 deferring tuning knobs in D-10 there).
- The launcher (D-04) + manifest (D-08) together are the reusable, documented recipe that Phase 4
  will generalise into the multi-scenario sweep (S2). Build them so they extend to scenarios.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ALLOCATION_REGION_FILTER` + `ALLOCATION_YEAR_POST_FILTER` env knobs already exist — D-01
  (per-region jobs) and D-09 (timestep resume) reuse them with no new driver logic.
- The timestep loop + posterior→anterior chaining already exists (`src/allocation.r:1514-1543`);
  it has only ever run with a single-timestep filter. The phase's job is to run it unfiltered and
  fix what breaks (D-05 collision, D-11 schedule).
- The per-timestep mosaic already produces `posterior_<year>.tif` via `terra::merge` + `extend`
  to full extent (`src/allocation.r:1789-1810`) — the post-hoc assembly job (D-03) reuses this
  logic, just driven over per-region posteriors after the fact.
- `saturation_summary.csv` + `AUDIT stage=saturation` + `src/saturation_diagnostics.r` (3.3)
  already compute per-region per-timestep saturation — D-07 just collects them; no new metric code.
- `scripts/submit_allocation*.sh` family + `verify_phase3_smoke.sh` — templates for the launcher
  (D-04) and manifest/checker (D-08).

### Established Patterns
- Per-region work_dir layout `outputs/simulations/{scenario}/{year}/region_{label}/` (3.3) —
  per-region posteriors live here; the shared `scenario/<year>/posterior_<year>.tif` is the
  national mosaic path (the D-05 collision point under parallel jobs).
- Env-var run scoping (`ALLOCATION_*_FILTER`, `ALLOCATION_PROFILE`, `profile_timestep_index`) is
  the established way to subset a run without code changes — extend it, don't replace it.
- `PROFILE` / `AUDIT` / `STATE` / `SENTINEL` structured log lines (Phases 1-3.3) — the manifest
  and plausibility checker should emit the same structured-line convention.

### Integration Points
- **D-05 collision (must-fix):** under per-region parallel jobs, the region-agnostic mosaic write
  at `src/allocation.r:1804` is a shared-path write multiple jobs hit concurrently — and the
  chained anterior returned to the loop is that mosaic, not the region's own posterior. Per-region
  chaining must read the region's own posterior; the national mosaic moves to a post-hoc step.
- **D-11 rate-table dependency:** allocation reads `BAU-<region>-trans_rates-<year_ant>.csv` per
  timestep (`prepare_region_worker_inputs`, ~791). Every `year_ant` in the chosen schedule needs
  a CSV — verify presence on HPC before launching; a missing one is a Stage-4 re-run prerequisite.
- The Dinamica launch path (`run_allocation_dinamica()` → `exec_dinamica()` →
  `resolve_dinamica_launch()`) is unchanged — this phase touches orchestration/IO, not the
  Dinamica contract.

</code_context>
