### CR-01 engine guard (D-01) — VERIFIED

`src/implement_spatial_interventions.R` ~L337-352, immediately after `terra::extract()`:

1. `!is.numeric(v)` is checked **first** — correct, because `!=` is meaningless on a
   factor. Message: `is categorical/non-numeric; expected numeric {0,1,NA}`.
2. Then `v[!is.na(v) & v != 0 & v != 1]` → `has value(s) outside {0,1,NA}: ...`.
3. The LUT is built only after both checks pass.

Fixtures in `test-spatial-interventions.R` cover a 255-valued mask, a categorical mask
and a 1-coded control. 63 tests, 0 failures.

### CR-01 pre-flight (D-02) — VERIFIED

`src/allocation.r` ~L650-700. Order: `nlyr` → `terra::is.factor` → `terra::minmax(compute
= TRUE)` range check → `compareGeom`. The range check is guarded by `all(is.finite(mm))`,
so an all-NA mask does not crash it with "missing value where TRUE/FALSE needed" (itself
a forbidden marker). A wiring test pins this. Out-of-domain, categorical, valid-silent and
all-NA fixtures: 43 tests, 0 failures.

**Design note, not a gap — the two halves are not equally strict.** The pre-flight only
rejects values outside the *range* `[0,1]`, because `minmax` is all it looks at. A
fractional mask (every cell `0.5`, say) has `min == max == 0.5` and therefore **passes**
the pre-flight, then stops at the D-01 runtime guard once a region is reached. So the
"fail before any region work starts" property holds for the 255-style and categorical
cases this phase was built for, but not for fractional values. That is inherent to the
cheap `minmax` design the plan chose for D-02 and is not a defect against any must-have;
it is recorded here so nobody later mistakes the pre-flight for a complete mirror of the
runtime guard.
